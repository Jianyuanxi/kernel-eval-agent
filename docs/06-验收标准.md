# 06 验收标准

两层：每块自己的完成标准（在 `docs/tasks/块N-*.md` 的“验收标准”一节），和整个系统的验收（本文）。系统验收由块 6 的一键脚本 `acceptance/run_samples.py` 跑，结果贴进最终报告和 PPT。

## 1. 系统验收（全部在服务器上、真实模式下跑）

| 编号 | 项目 | 标准 | 怎么测 |
|---|---|---|---|
| S1 | 样例走通 | 样例 1、样例 4、样例 2 的 lab10 和 lab6_pro、样例 3 都能从上传走到出报告（stage=done） | 一键脚本 |
| S2 | 多工程识别 | 样例 2 上传后识别出 11 个工程，名字对得上 lab 目录名 | 一键脚本 |
| S3 | 片段模式 | 样例 3 识别为 fragment，没有编译运行，报告里扫描覆盖率如实显示，总分按 80 分折算 | 一键脚本 |
| S4 | 耗时 | S1 里能出报告的正常样例，单次评测（从开始到 done）不超过 5 分钟；出错的情况（死循环、智能体超时）靠各步硬上限结束，不卡死队列 | 一键脚本记录耗时 |
| S5 | 稳定 | 样例 1 评两次，总分相差不超过 5 分 | 一键脚本 `--repeat 2` |
| S6 | 位置真实 | 报告里所有缺陷、功能点、创新点引用的文件都存在、行号在 1 到文件行数之间（后端会自动去掉不合法的，这里检查最终报告） | 一键脚本逐条检查 |
| S7 | 工具调用 | 每份报告的工具记录里，智能体（source=agent）调用了必调工具（read_source 至少一次成功），并有至少一次知识库检索 | 一键脚本 |
| S8 | 检出率 | 植入的 10 个缺陷，完整系统至少检出 6 个；同时给出只用 clang 的检出数做对比 | 块 4 统计脚本 |
| S9 | 容错 | 上传 txt、损坏的 zip、编译不过的工程（改错一行）、死循环内核，都给出明确提示，服务不崩 | 一键脚本 + 手工 |
| S10 | 追问 | 对样例 1 的一条缺陷追问，30 秒内得到相关回答，报告分数不变 | 一键脚本 |
| S11 | 导出 | 能导出 JSON 和 Markdown，Markdown 里有总分、分项、缺陷清单 | 一键脚本 |
| S12 | 页面 | 报告页能看到：总分和等级、四项分数和雷达图、8 个功能点、缺陷清单（级别、位置、知识点、建议、改前改后）、工具调用过程 | 手工截图 |

## 2. 和任务原文逐条对照

| 任务原文要求 | 对应 |
|---|---|
| 接收内核 C 源码（文件上传） | F1、S1、S2、S3 |
| 调用 clang 静态分析工具扫描 | F4、块 4 |
| 源码 + 分析报告提交大模型 | 智能体通过 read_source、clang_scan 工具取得，S7 |
| 自动识别代码缺陷 | F5、S6、S8 |
| 结合操作系统知识点给出解释 | 知识库 + 每条缺陷的 knowledge 字段，F6 |
| 给出修改建议 | 每条缺陷的 suggestion、before/after |
| 给出分项评分 | docs/03 四项评分，S12 |
| 结果输出 | F7、S11、S12 |
| 演示智能体的工具调用能力 | F8、S7、报告页工具调用过程 |
