# 01 总体设计

## 1. 要做什么

任务原文：小组开发操作系统内核代码评测智能体。该智能体接收简易内核模块 C 源码，调用 clang 静态分析工具扫描代码，将源码与分析报告提交大模型，自动识别代码缺陷，结合操作系统知识点给出解释、修改建议与分项评分。要求实现文件上传、结果输出功能，演示智能体工具调用能力。

做出来是一个网站：上传一份 MiniEuler 内核代码 → 系统在沙箱里编译、在 QEMU 里运行、用 clang 扫描、和参考代码对比 → 智能体调用工具取回这些结果、读源码、查知识库 → 输出评测报告（总分、分项、功能点、缺陷清单、知识点讲解、修改建议、工具调用过程），可导出、可就某条缺陷追问。

## 2. 架构

```text
浏览器 ──80──▶ nginx ──┬─ /            前端静态文件（Vue）
                       ├─ /api/*  ──▶ 后端 FastAPI（127.0.0.1:8000，systemd 服务）
                       └─ /tools/* ─▶ 同上（给 Dify 调的工具接口，带令牌）

后端 ─┬─ 评测流水线（单线程队列）
      │    整理 → 编译 → 运行 → 扫描 → 对比 → 智能体评审 → 校验 → 评分 → 报告
      ├─ 沙箱：每步起一个一次性 Docker 容器（断网、非 root、限资源）
      ├─ 文件存储：/data/kernel-eval/tasks/{task_id}/（不用数据库）
      └─ Dify API（127.0.0.1:8080/v1，流式 chat-messages）

Dify 1.17.1（Docker Compose，8080）── Agent 应用 ─┬─ 大模型：TokenHub deepseek/deepseek-flash
                                                ├─ 知识库：操作系统知识点（向量 + 关键词混合检索）
                                                └─ 自定义工具：经公网 IP 回调我们的 /tools/*
```

| 部分 | 用什么 |
|---|---|
| 后端 | Python 3.12 + FastAPI + Pydantic，单进程，文件存储 |
| 前端 | Vue 3 + Vite + JavaScript，轮询进度（1–2 秒），ECharts 画雷达图 |
| 智能体平台 | Dify 1.17.1（自部署，固定版本） |
| 大模型 | 腾讯云 TokenHub：deepseek/deepseek-flash，备选 glm-5.3-flash |
| 向量模型 | kinfra-text-embedding-0.6b |
| 编译运行 | aarch64-none-elf-gcc 13.3 + CMake + QEMU 8.2（沙箱镜像） |
| 静态分析 | clang 18 `--analyze`，逐文件扫描 |
| 部署 | 腾讯云轻量服务器（成都），nginx + systemd，Dify 用官方 Compose |

## 3. 为什么这样设计

**必做步骤由后端保证，智能体负责判断。** 编译、运行、扫描、对比在智能体开始前就由流水线跑完存好；智能体调用工具时拿的是存好的结果。这样：

- 模型漏调工具也不会漏扫（漏调了后端会提醒它一次，仍不调就判失败）；
- 重复调用不会重复编译，评测时间可控（目标 10 分钟内）；
- 工具调用过程照样完整记录下来展示（流水线 4 条 + 智能体十几条）。

**分数由代码算，不让模型算。** 模型只判断功能点完成情况、找缺陷、评规范档次；缺陷级别由缺陷类型决定，扣分和总分按 docs/03 的固定规则算。同一份代码两次的分数才稳定。

**模型的输出要校验。** 智能体最后输出一个 JSON；后端检查格式、文件和行号是否真实存在、引用的证据编号是否存在。格式不对让它改一次，还不对就判失败，不出一份假报告。

**参考代码对比（创新点 C）。** 这门课的作业是在参考实验代码上改，学生原样保留的文件里的问题不该扣学生的分。对比后：和参考代码完全相同的文件里的缺陷只展示、不扣分；落在学生改动行里的缺陷单独标出。

**接口先冻结，各块并行。** schemas、示例数据、工具接口、模块函数签名在开工前定死（docs/02）。每块用 `contracts/examples/` 里的示例数据和 `KE_MOCK_MODULES` 假数据开发，不用等别人。

## 4. 一次评测的流程

| 步骤 | 谁做 | 产出 | 工具记录 |
|---|---|---|---|
| 上传、解压、识别工程 | 块 2 | IngestResult，用户选一个工程 | |
| 编译（完整工程） | 块 3 | BuildResult | pipeline / compile_project |
| 运行（编译通过时） | 块 3 | RunResult | pipeline / run_kernel |
| clang 扫描 | 块 4 | ScanResult | pipeline / clang_scan |
| 和参考代码对比 | 块 2 | DiffResult | pipeline / diff_reference |
| 智能体评审 | 块 5 的 Dify 应用，块 1 调用 | ReviewResult | agent / 各工具 + knowledge |
| 校验缺陷、打标记 | 块 1 | ReportDefect 列表 | |
| 评分 | 块 6 | ScoreResult | |
| 组装报告、展示、导出、追问 | 块 1、6 | Report、网页 | followup / 各工具 |

## 5. 必须完成的功能

| 编号 | 功能 | 怎样算完成 | 负责 |
|---|---|---|---|
| F1 | 文件上传（zip 或 .c） | 4 份样例都能上传，页面显示识别出的工程 | 块 2、6 |
| F2 | 编译检查 | 完整工程能编译通过；改错一行后能报出错误位置 | 块 3 |
| F3 | 运行检查 | 能看到内核启动后的输出；每次运行最多 20 秒，内核卡死也会自动结束（没有输出时换 GIC 版本重试一次，整个运行不超过 1 分钟） | 块 3 |
| F4 | clang 静态分析 | 能给出扫描结果；植入一个空指针错误能被扫出来 | 块 4 |
| F5 | 智能体评审 | 输出缺陷清单（级别、位置、知识点解释、修改建议）、功能点完成情况、分项评分和总评 | 块 5、6 |
| F6 | 知识库检索 | 知识点讲解和缺陷类型对得上 | 块 5 |
| F7 | 结果输出 | 网页展示报告，可导出文件 | 块 6 |
| F8 | 工具调用过程展示 | 报告里能看到智能体依次调用了哪些工具 | 块 1、6 |

## 6. 创新点

| 编号 | 内容 | 负责 |
|---|---|---|
| A 植入缺陷测试 | 在样例里人为植入 10 个已知缺陷做测试集，统计检出率，和只用 clang 的结果对比 | 块 4 |
| B 追问 | 报告页里就某条缺陷继续问智能体，复用评测时的会话 | 块 6（块 5 调提示词） |
| C 找出学生改了什么 | 和参考实验代码对比，标出学生改动和新增的部分；参考代码原有的问题不扣分 | 块 2 |

## 8. 阶段安排

不规定日期，按阶段推进；有时间可以一次连着做完几个阶段，但每个阶段单独提 PR。项目 11 月末交付。

| 阶段 | 目标 |
|---|---|
| 阶段 1：第一版 | 各块用假数据把自己的模块做出可运行的第一版并合进 main；块 1 + 块 5 打通真实智能体关卡（样例 1：真实工具回调、JSON 校验通过、一次追问） |
| 阶段 2：真实样例 | 各块用真实样例完善；块 1 逐个把模块从假数据切成真实，服务器上样例 1 真实跑通 |
| 阶段 3：全部走通 | 4 份样例全部走通；块 4 跑植入缺陷统计；块 6 跑一键验收；修问题 |
| 阶段 4：收尾 | 稳定性和耗时达标；各块写指导书自己那章；块 1 汇总 Word 指导书；演示彩排。答辩 PPT 全组到时一起做 |

前一阶段的依赖没好时，用假数据先做后面的部分，不用等。每块的详细安排见 `docs/tasks/`。
