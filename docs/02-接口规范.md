# 02 接口规范（冻结）

本文和 `backend/app/schemas/`、`contracts/` 一起构成全组的接口契约。**字段以 schemas 代码为准**，本文讲规则和约定；示例数据见 `contracts/examples/`（用样例 1 的真实结果生成）。

改接口的规矩见第 10 节。开工后原则上不改。

## 1. 编号与路径

| 东西 | 规则 | 例子 |
|---|---|---|
| 任务编号 task_id | `t` + 北京时间 `yyyymmddHHMMSS` + 6 位随机十六进制，由块 1 生成 | `t20261020153000a1b2c3` |
| 工程编号 project_id | `p1`、`p2`……按工程根目录路径字典序编号，由块 2 生成 | `p1` |
| 文件路径 | 相对**工程根**，分隔符统一 `/`，不以 `/` 或 `./` 开头 | `src/shell/shmsg.c` |
| 行号 | 从 1 开始；行范围是闭区间 | `{"start": 96, "end": 96}` |
| 文件行数 | 按 `\n` 计，`\r\n` 算一个；最后一行没有换行也算一行；空文件 0 行；空行照常计数（只有和参考代码对比时才去掉末尾空行） | 样例 1 `src/main.c` 71 行 |
| 时间 | ISO 8601 带时区，北京时间，精确到秒 | `2026-10-18T16:30:01+08:00` |
| 结果状态 Status | `passed` / `failed` / `timeout` / `skipped` / `unsupported` / `error` | |

**状态的含义要分清**：`failed` 是学生代码的问题（编译不过、内核没启动）；`error` 是我们工具自己的问题（docker 起不来）。两者不能混用，评分时处理不同。

## 2. 证据编号

工具结果里的每一条可引用的东西都有编号，智能体在报告里用编号引用，块 1 校验编号是否真实存在。

| 前缀 | 来自 | 谁分配 | 规则 |
|---|---|---|---|
| B | 编译诊断（警告/错误） | 块 3 | 按日志出现顺序 B1、B2…，最多 100 条 |
| R | 运行输出 | 块 3 | R1 = 启动输出；R2、R3… = 依次发送的 shell 命令的输出 |
| C | clang 告警 | 块 4 | 去重后按 (path, line) 排序编号 C1、C2…，最多 100 条 |
| D | 与参考代码的差异 | 块 2 | 按路径排序，只给 modified / added 文件编号；same 文件为空串 |
| S | 智能体读源码 | 块 1（工具层） | 每次 read_source 调用分配一个，任务内递增；模块函数返回空串即可 |

## 3. 任务目录

数据根目录 `KE_DATA_ROOT`（服务器 `/data/kernel-eval`，本机默认 `backend/data`）。一个任务的全部文件：

```text
tasks/{task_id}/
├─ meta.json              TaskInfo（块 1 写）
├─ upload/                原始上传文件（块 1 写）
├─ unpacked/              解压并过滤后的全部文件（块 2 写）
├─ projects/{pid}/        每个工程一份拷贝，原样不改（块 2 写；后面所有步骤只读）
├─ work/{pid}/build/      编译工作副本：拷贝 + 工具链改写 + build/ 产物（块 3 写）
├─ work/{pid}/scan/       扫描工作副本（块 4 写）
├─ logs/{pid}/            build.log、run.log、scan.log、agent_answer.txt
├─ results/{pid}/         build.json run.json scan.json diff.json review.json score.json（块 1 写）
├─ tool_calls.jsonl       ToolCallRecord，一行一条（块 1 写）
└─ report.json            Report（块 1 写）
```

- 只能写自己负责的目录。`projects/` 是原件，任何模块都不能改。
- 写 JSON 一律用 `storage.write_json`（先写临时文件再改名）。
- 结果里出现的日志路径一律相对任务目录（如 `logs/p1/build.log`）。

## 4. 模块函数（签名冻结）

块 1 的流水线按下面的签名调用各模块，**签名、参数含义、返回类型都不能改**。每个模块内部怎么拆文件自己定。

| 模块 | 函数 | 返回 | 说明 |
|---|---|---|---|
| 块 2 `app.ingest` | `ingest_upload(task_dir, upload_paths, upload_name)` | IngestResult | 失败返回 status=failed + error，不抛异常 |
| | `list_files(project_dir, project_id)` | FileList | 工程内全部文件，按路径排序 |
| | `read_source(project_dir, path, start_line, end_line)` | SourceSlice | 一次最多 200 行，超出文件末尾就截断；非法路径抛 `PathInvalidError` |
| | `diff_reference(project, project_dir, ref_root)` | DiffResult | 创新点 C |
| | `change_flags(diff, path, line)` | (bool\|None, bool) | 给缺陷打标记，语义见第 8 节 |
| 块 3 `app.buildrun` | `build(project, project_dir, work_dir, log_dir)` | BuildResult | |
| | `run(project, work_dir, build_result, log_dir)` | RunResult | |
| | `sandbox.run_in_sandbox(cmd, work_dir, timeout_s, *, name, stdin_steps, max_output)` | ExecResult | 公共沙箱执行器，块 4 也用 |
| | `sandbox.prepare_workspace(project_dir, work_dir)` | list[str] | 拷贝工程并改写工具链路径，块 4 也用 |
| 块 4 `app.analyze` | `scan(project, project_dir, work_dir, log_dir)` | ScanResult | |
| 块 6 `app.scoring` | `compute_score(project, build, run, review, defects)` | ScoreResult | 纯函数；就地设置 `defects[i].counted` |
| | `render_markdown(report)` | str | 导出用 |
| 块 6 `app.followup` | `answer_followup(report, req, dify)` | FollowupResponse | 创新点 B |

共同要求：

- 学生代码有问题（编译不过、扫不了）用返回值里的 status 表达，**不要抛异常**。只有我们自己的工具坏了才抛 `SandboxError`（块 1 转成 status=error）。
- 函数里耗时操作都有超时：编译 `KE_BUILD_TIMEOUT_S`（180 秒）、运行窗口 `KE_RUN_WINDOW_S`（20 秒；没有输出时换 GIC 版本再跑一次，整个 run 在 2×RUN_WINDOW_S+20 秒内返回）、扫描 `KE_SCAN_TIMEOUT_S`（300 秒）。智能体评审总共 `KE_AGENT_TIMEOUT_S`（420 秒，首次、提醒、修正共用这一个预算；流式连接 30 秒收不到任何数据算断线），追问 `KE_FOLLOWUP_TIMEOUT_S`（60 秒）。
- 不读写第 3 节以外的路径；需要配置项从 `app.config` 读。

## 5. 网页接口（/api，块 1 提供，块 6 使用）

出错统一返回 HTTP 4xx/5xx + `{"error": {"code": "...", "message": "..."}}`，前端按 code 提示、显示 message。请求参数不合法（缺字段、类型不对、start=0 等）返回 422 + `REQUEST_INVALID`。

| 方法 | 路径 | 请求 | 返回 | 说明 |
|---|---|---|---|---|
| GET | `/api/health` | | `{ok, mock_modules, sandbox_image}` | |
| POST | `/api/tasks` | multipart，字段名 `files`：一个 `.zip`，或 1–50 个 `.c/.h` | TaskInfo | 返回时已经整理完：stage=waiting_select 或 failed |
| GET | `/api/tasks/{id}` | | TaskInfo | 轮询进度，前端每 1–2 秒一次 |
| POST | `/api/tasks/{id}/start` | `{"project_id": "p1"}` | TaskInfo | 只有 waiting_select 能开始，否则 409；只有一个工程时前端自动调 |
| GET | `/api/tasks/{id}/events?after=N` | | EventsResponse | seq > N 的工具调用记录，用来实时显示过程 |
| GET | `/api/tasks/{id}/report` | | Report | stage≠done 时 409 RESULT_NOT_READY |
| GET | `/api/tasks/{id}/export?format=json\|md` | | 文件下载 | |
| GET | `/api/tasks/{id}/source?path=&start=&end=` | | SourceSlice | 报告页点缺陷时看源码，最多 200 行 |
| POST | `/api/tasks/{id}/followup` | FollowupRequest | FollowupResponse | 只能在 done 之后 |

任务阶段（stage）依次是：`uploaded → waiting_select → queued → building → running → scanning → diffing → reviewing → scoring → done`，任一步出错进 `failed`（看 error.code）。代码片段工程没有 building/running。服务重启时没跑完的任务一律标 failed。

上传限制：上传总大小 20MB；解压后总大小 100MB、文件数 5000（`app.config`）。

## 6. 工具接口（/tools，块 1 提供，块 5 接入 Dify）

接口描述在 `contracts/tools.openapi.yaml`，直接导入 Dify 的自定义工具。

- 全部 `POST` + 扁平 JSON，必须带请求头 `X-Tool-Token`（值是服务器配置里的 `KE_TOOL_TOKEN`），错了返回 401。
- 除令牌错误外，出错一律 **HTTP 200** + `{"error": {...}}`，让模型能读到原因；参数不合法同样是 200 + `REQUEST_INVALID`。
- 编译、运行、扫描、对比返回流水线**已经存好的结果**，重复调用不会重复执行；每次调用都记一条 ToolCallRecord（评测中 source=agent，评测完成后 source=followup）。
- 返回给模型的内容会截短：文件列表 ≤300 条、编译诊断 ≤30 条、日志尾部 ≤1500 字符、clang 告警 ≤50 条、差异只列非 same 文件且 ≤80 个、源码每次 ≤200 行。

| 工具（operationId） | 参数 | 返回 | 证据编号 |
|---|---|---|---|
| list_files | task_id, project_id | FileList | |
| read_source | task_id, project_id, path, start_line=1, end_line=200 | SourceSlice | S |
| compile_project | task_id, project_id | BuildResult | B |
| run_kernel | task_id, project_id | RunResult | R |
| clang_scan | task_id, project_id | ScanResult | C |
| diff_reference | task_id, project_id | DiffResult | D |

知识库检索是 Dify 自带的，不经过我们的工具接口；块 1 从 Dify 的 agent_thought 事件里补记一条 tool=knowledge 的记录。

**必调工具**：完整工程必须调 compile_project；编译通过时必须调 run_kernel；所有工程必须调 clang_scan、至少一次**成功的** read_source（status=passed，路径错误的不算）、至少一次知识库检索（tool=knowledge）。编译失败、扫描 unsupported 也是有效结果，照样算调过。智能体漏调时块 1 提醒一次，仍漏调则任务失败（AGENT_SKIPPED_TOOLS）。

## 7. 已在服务器上验证的规则（2026-10-18，样例 1–4）

块 3、4 直接按这些做，不用再摸索。沙箱镜像见 `sandbox/`。

**工具链路径**：学生 CMakeLists 里的工具链路径五花八门（`set(TOOLCHAIN_PATH /root/aarch64-none-elf)`、`/opt/buildtools/gcc-arm-10.3-2021.07-x86_64-aarch64-none-elf/bin/...`、`${TOOLCHAIN_PATH}`）。在工作副本里用两条正则统一改成 `/opt/toolchain`（已实现在 `sandbox.prepare_workspace`）：

```text
set\(\s*TOOLCHAIN_PATH\s+"?[^\s)"]+"?\s*\)   →  set(TOOLCHAIN_PATH /opt/toolchain)
/[^\s"()]*?/bin/aarch64-none-elf-            →  /opt/toolchain/bin/aarch64-none-elf-
```

改写后样例 1、4 和样例 2 的 11 个 lab（lab1/2/2_hw1/4/5/5_pro/6/6_pro/8/9/10）全部能编译。

**编译**：`cmake -S src -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON && cmake --build build -j2`（工程根下有 `src/CMakeLists.txt` 时；否则 `-S .`）。

**产物**：依次找 `build/miniEuler`、`build/miniEuler.elf`，再找 `build/` 下任意 `*.elf`。

**GIC 版本**：取 `runMiniEuler.sh` 里最后一个 `gic-version=(\d)`；没有运行脚本就在源码注释里找（样例 2 lab10 在 `cpu_config.h` 里写了 gic-version=3）；都没有用 2。**没有任何串口输出时换另一个版本重试一次**。

**QEMU 命令**（`-nic none` 必须加，否则报找不到 efi-virtio.rom）：

```text
timeout 20 qemu-system-aarch64 -machine virt,gic-version=N -m 1024M -cpu cortex-a53 -nographic -nic none -serial mon:stdio -kernel <产物>
```

退出码 124 是正常的窗口结束，不算失败。

**shell 交互**：样例 1 的提示符是 `miniEuler # `。不用等提示符，启动后等 4–5 秒开始发，每 2 秒发一条，每条命令以 `\r` 结尾（例如 `top\r`、`tick\r`、`mem\r`）。

**串口输出整理**：`\r\n` → `\n`，再把连续的空行合并成一个换行（原始输出每行后面会多一个空行）。

**异常刷屏**：样例 2 lab6_pro 会不停打印 `Catch a exception.`（20 秒 5MB）。同一非空行在输出中出现 ≥50 次记为 `EXC_STORM`，运行状态 failed；输出最多保留 256KB，超过记 `OUTPUT_TRUNCATED`。

**算启动成功**：有任何不是 QEMU 自己打印的串口输出就算 booted（lab1 只打印 `AArch64 Bare Metal` 也算）。

**clang 扫描**：每个 .c 文件单独执行（参数从 `compile_commands.json` 取该文件的 `-I/-D/-include/-std`）：

```text
clang --analyze --target=aarch64-none-elf -ffreestanding -fno-builtin \
  -Wno-error=implicit-function-declaration -Wno-error=implicit-int -Wno-error=int-conversion \
  -Wno-error=incompatible-pointer-types -Wno-error=incompatible-function-pointer-types \
  -Xclang -analyzer-output=plist -o X.plist <-I -D ...> file.c
```

样例 1 结果：15 个 C 文件扫成 14 个（`prt_sched_single.c` 报 conflicting types for 'OsMainSchedule'，记进 files_failed），7 条告警（`main.c:57` DeadStores，`vsnprintf_s.c` 6 处 NullDereference）。

**代码片段（样例 3，RISC-V）**：缺头文件，补空头文件也扫不成，记 status=unsupported 并给出覆盖率；智能体直接读源码评审。不能当作“零缺陷”。

**和参考代码对比**：参考仓库 <https://gitee.com/leeboby/os2024_exp_redo_kp>，固定 commit `0bd1ef59f32867842f0c3047a58d62bced82d54b`，服务器 `/data/kernel-eval/ref/os2024_exp_redo_kp`。

- 每行去掉 CRLF 和行尾空白、去掉文件末尾空行后再比较
- 基线选和学生工程**同路径文件最多**的 lab，并列取编号大的
- 样例 1 → lab10：相同 14、修改 26、新增 10（候选：lab1 7、lab2 9、lab4 11、lab5 19、lab6 32、lab7 37、lab8 39、lab10 40）
- 样例 4 → lab10：相同 49、修改 9、新增 3

## 8. 缺陷的校验与标记（块 1 做）

智能体输出的 ReviewResult 经块 1 处理后才进报告（`pipeline._finalize_defects`）：

1. 文件不存在或行号超过文件行数 → 丢弃，写进 `report.warnings`；功能点和创新点的 locations 同样校验，不合法的位置去掉并写 warnings（判断本身保留）
2. (path, line, type) 相同的只留第一条
3. 引用了不存在的证据编号 → 去掉该编号，写进 warnings
4. 按 `DEFECT_TYPES` 补上中文名、级别、知识点（**级别由类型决定，模型不能改**）
5. 用 `change_flags` 打两个标记：
   - `in_baseline_unchanged`：缺陷所在文件和参考代码完全相同 → 只展示，不扣分
   - `in_student_change`：缺陷行落在学生改动/新增的行范围里；没有基线时为 null

`change_flags(diff, path, line)` 的语义（`app/core/mocks.py` 里有参考实现）：diff 为空或 status≠passed → (None, False)；文件 same → (False, True)；modified/added → (行在任一 hunk 内, False)；文件不在 diff 里 → (None, False)。

## 9. 智能体的输出格式

见 `backend/app/schemas/review.py` 的 ReviewResult 和 `contracts/examples/review_result.json`。要点：

- `features` 恰好 8 项：F_UART 串口打印、F_EXC 异常处理、F_TIMER 时钟中断、F_TASK 任务创建与切换、F_SCHED 任务调度、F_SEM 信号量、F_SHELL shell 命令、F_INNOV 创新功能；status 为 done / partial / none
- `defects` 最多 30 条，type 只能用 24 个缺陷类型代码之一（`schemas/common.py`）
- `source`：clang / gcc / llm / clang+llm / gcc+llm
- 智能体**不打分**，分数由块 6 按 docs/03 计算

输出不合格式时块 1 发一次修正请求（`agent/prompts/repair.md`），仍不合格任务失败（REVIEW_INVALID）。

## 10. 改接口的规矩

- **兼容的改动**（给模型加一个有默认值的可选字段）：在 PR 里说明，同步更新 `contracts/examples/`，`pytest` 通过即可合并。
- **不兼容的改动**（改名、删字段、改类型、改函数签名、改枚举值、改评分规则）：先在群里说，组长同意后由块 1 改 schemas 和示例，再通知所有人。
- 不允许为了让自己的测试通过而改 schemas、示例或别人的测试。
- `backend/app/schemas/`、`contracts/`、`backend/app/core/`、`backend/requirements.txt` 归块 1；其他人要改提 PR 由块 1 合并。
