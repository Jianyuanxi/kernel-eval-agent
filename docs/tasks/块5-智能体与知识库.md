# 块 5：智能体与知识库

> 给负责本块的同学和他的 AI 看。先读仓库根目录 `AGENTS.md`，再读本文。相关规范：`docs/02-接口规范.md` 第 5、8、9 节，`docs/05-服务器与环境.md` 第 6 节，`backend/app/schemas/review.py`。

## 1. 目标

在 Dify 里搭出评测智能体：它调用我们的工具（编译、运行、clang 扫描、读源码、对比参考代码）、检索操作系统知识库，最后输出符合 `ReviewResult` 格式的 JSON（功能点判断、缺陷清单、知识点讲解、修改建议、规范评价、创新评价）。**智能体不打分**，分数由块 6 的代码算。

这一块决定“演示智能体工具调用能力”和“结合操作系统知识点给出解释”两条任务要求能不能做好。

## 2. 范围

- 只改 `agent/`（`prompts/`、`knowledge/`、`dsl/`、`README.md`）和 Dify 里的应用、知识库。
- 提示词的占位符（`{task_id}` 这类）由 `backend/app/core/prompts.py` 填，**占位符名字不能改、不能删**；文字可以随便调。每个提示词文件开头的 `<!-- -->` 注释会被去掉，不会发给模型。
- 不改后端代码。要改工具返回内容、截短规则，找块 1。

## 3. 准备

1. **Dify 账号**：组长在 Dify 后台邀请你（没配邮件，组长会把激活链接发给你），登录 <http://132.232.242.186:8080/>。
2. **模型**：组长已在“设置 → 模型供应商”里用 OpenAI-API-compatible 插件接好腾讯云 TokenHub：
   - 主模型 `deepseek/deepseek-flash`（函数调用模式，Tool Call）
   - 备选 `glm-5.3-flash`
   - 向量模型 `kinfra-text-embedding-0.6b`
   - 没有重排模型
   你不需要也拿不到 TokenHub 密钥。
3. **工具令牌**：`ssh kernel-eval` 后 `grep ^KE_TOOL_TOKEN= /opt/kernel-eval/kernel-eval.env`。只填进 Dify，不要写进仓库或聊天记录以外的文件。

## 4. 要做的事

### 4.1 自定义工具

Dify → 工具 → 自定义 → 创建自定义工具：

- 名称 `kernel_eval_tools`，Schema 粘贴 `contracts/tools.openapi.yaml` 全文（服务器地址已经是 `http://132.232.242.186`，不要改成内网地址，内网会被 Dify 的 SSRF 代理拦掉）。
- 鉴权：API Key，类型“自定义请求头”，请求头名 `X-Tool-Token`，值填工具令牌。
- 导入后应该看到 6 个工具：list_files、read_source、compile_project、run_kernel、clang_scan、diff_reference。在 Dify 里点“测试”调一下 list_files（task_id 用服务器上已有的任务，`ls /data/kernel-eval/tasks/` 可以看到）确认能通。

### 4.2 知识库

在 `agent/knowledge/` 下写 Markdown 知识文档（**自己写的总结**，不要整段复制教材或网页），按知识点分类一类一个文件：

| 文件 | 知识点（`schemas/common.py` 的 KnowledgeCategory） | 要覆盖的缺陷类型 |
|---|---|---|
| `K_MEM-内存管理.md` | 内存的分配与回收 | USE_AFTER_FREE、DOUBLE_FREE、MEM_LEAK |
| `K_ADDR-地址空间与内存保护.md` | 地址空间与内存保护 | NULL_DEREF、OUT_OF_BOUNDS、WILD_POINTER |
| `K_SYNC-同步互斥与死锁.md` | 进程同步与互斥、死锁四个必要条件 | DEADLOCK、LOCK_NOT_RELEASED、LOCK_ORDER |
| `K_CRIT-临界区与竞态.md` | 临界区、竞态条件 | RACE |
| `K_IRQ-中断机制.md` | 中断机制 | IRQ_NOT_RESTORED、IRQ_LONG_WAIT |
| `K_CTX-上下文切换.md` | 进程控制块与上下文切换 | CONTEXT_SAVE |
| `K_SYSCALL-系统调用.md` | 系统调用、用户态与内核态 | UNCHECKED_PARAM |
| `K_DEV-设备与资源.md` | 文件系统与设备管理 | RESOURCE_NOT_CLOSED |
| `K_GENERAL-编程规范.md` | 通用编程规范与健壮性 | DIV_ZERO、UNINIT_VAR、UNCHECKED_RETURN、UNUSED、MAGIC_NUMBER、NO_COMMENT |
| `MiniEuler-实验要点.md` | 8 个功能点在 MiniEuler 里一般怎么实现、关键函数和文件 | F_UART … F_INNOV |

每个缺陷类型一节，写：概念（2–3 句）、在内核里为什么危险、MiniEuler/ARM64 里的典型写法（比如 `prt_sem.c` 里 `OsIntLock()` 关中断后每个返回分支都要 `OsIntRestore(intSave)`，切换任务前用 `OsTskScheduleFastPs(intSave)`）、怎么改。每节以 `## 缺陷类型代码 中文名` 开头，方便切段。

Dify → 知识库 → 创建：

- 名称 `os-knowledge`，导入 `agent/knowledge/` 全部文件
- 分段：自定义，分隔符 `\n## `，最大长度 800
- 索引：高质量，向量模型 `kinfra-text-embedding-0.6b`
- 检索：混合检索，权重设置（语义 0.7 / 关键词 0.3），Top K 4，不开重排

### 4.3 智能体应用

Dify → 创建应用 → **Agent**（不是工作流、不是 Chatflow），名称 `kernel-eval-agent`：

- 模型 `deepseek/deepseek-flash`，Agent 设置里选**函数调用（Function Calling）**，最大迭代次数 20
- 指令：粘贴 `agent/prompts/system.md`（去掉开头注释）
- 工具：添加 `kernel_eval_tools` 的 6 个工具
- 知识库（上下文）：添加 `os-knowledge`
- 开场白、建议问题都关掉
- 发布

然后“访问 API → API 密钥 → 创建”，得到 `app-` 开头的密钥，**私聊发给块 1**（填进服务器的 `KE_DIFY_APP_KEY`），不要进仓库。

### 4.4 第 1 周关卡（和块 1 一起）

块 1 把服务器上部署的服务改成“只有智能体是真实的”（`KE_MOCK_MODULES=ingest,buildrun,analyze,diff,scoring`，填好 `KE_DIFY_APP_KEY`），然后：

1. 打开 <http://132.232.242.186/docs>，用 `POST /api/tasks` 上传样例 1 的 zip（服务器上 `/data/kernel-eval/samples/样例1`，打包后上传；或者用块 6 的网页）
2. `POST /api/tasks/{id}/start`，`GET /api/tasks/{id}` 轮询到 done
3. 看 `GET /api/tasks/{id}/report`：

| 检查 | 要求 |
|---|---|
| 工具调用 | `tool_calls` 里 source=agent 的记录包含 compile_project、run_kernel、clang_scan、read_source，至少一条 knowledge |
| 格式 | stage=done（没有 REVIEW_INVALID、AGENT_SKIPPED_TOOLS） |
| 位置 | `warnings` 里丢弃的缺陷 ≤2 条 |
| 内容 | 能发现 `src/shell/shmsg.c` 里的数组越界（第 96 行附近）；每条缺陷的 knowledge 是操作系统知识点，不是空话 |
| 追问 | `POST /api/tasks/{id}/followup` 问一条缺陷，30 秒内有相关回答 |

不过关就调提示词、调知识库，重复直到过关。智能体没调某个工具时，后端会自动发 `agent/prompts/nudge.md` 提醒一次；JSON 不合格时会发 `repair.md` 让它修一次。看智能体每一步在想什么：Dify 应用的“日志与标注”，或者报告里的 `agent_thoughts`。

### 4.5 调提示词（第 2–3 周）

在样例 1、样例 4、样例 2 的 lab10 和 lab6_pro、样例 3 上逐个跑，改进：

- **功能点判断要有依据**：每个功能点的 locations 指向真实代码，status 和代码对得上
- **缺陷少而准**：宁可少报，不要编；source 写对（clang 原样采用写 clang，读代码确认写 clang+llm）
- **证据编号**：引用工具返回的 B/R/C/D/S 编号（docs/02 第 2 节），不要编不存在的编号
- **片段模式**（样例 3）：没有编译运行结果，clang 也扫不成，要靠 read_source 读代码评审
- **参考代码原有的问题**：diff_reference 显示文件 same 的，可以报但要在 description 里说明“参考代码原有”
- 对比 `deepseek/deepseek-flash` 和 `glm-5.3-flash`：同样的样例各跑 2 次，记录耗时、过关情况、缺陷质量，写进 `agent/README.md`，选定一个（块 1 改 `KE_MODEL_NAME`）

`agent/prompts/followup.md` 是追问模板（块 6 调用），回答要求：直接回答、不超过 300 字、可以调 read_source 看代码、**不改分数**。

### 4.6 导出与重建说明

- 每次在 Dify 里改完应用，导出 DSL（应用 → 导出 DSL）存成 `agent/dsl/kernel-eval-agent.yml` 提交（导出前确认不含密钥；工具令牌不会导出，但检查一遍）
- `agent/README.md` 写清楚从零重建的步骤：接模型、建工具、建知识库、建应用、导入 DSL、拿 app key。别人照着做能 15 分钟内重建

## 8. 常见坑

- Dify Agent 应用的知识库检索不走我们的工具接口；后端从 Dify 的 `agent_thought` 事件里认出名字以 `dataset_` 开头的工具，补一条 knowledge 记录。知识库要加在“上下文”里，不要做成工作流节点。
- 函数调用模式下模型偶尔一次并行调多个工具，没关系，后端每次调用都会记录。
- 模型输出 JSON 前后带说明文字也能解析（后端优先取 ```json 代码块），但 JSON 本身必须完整、字段名一个字不能错。
- 改了提示词记得在 Dify 里**重新发布**，否则 API 调的还是旧版本。
