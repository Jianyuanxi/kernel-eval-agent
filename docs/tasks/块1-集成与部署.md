# 块 1：集成与部署

> 给负责本块的同学和他的 AI 看。先读仓库根目录 `AGENTS.md`，再读本文。本块管所有公共部分，要通读 `docs/01`–`06`。

## 1. 目标

把六块拼成一个能用的系统并部署好：

1. 维护公共代码（编排流水线、存储、网页接口、工具接口、Dify 客户端、假数据、schemas、示例）。
2. 阶段 1 和块 5 一起打通**真实智能体关卡**。
3. 各块做好后，逐个把服务器上的模块从假数据切成真实，最后全部真实运行。
4. 部署、CI、审核合并 PR。
5. 汇总 Word 指导书（答辩 PPT 全组到时一起做，不在本块任务里）。

## 2. 范围

`backend/app/core/`、`backend/app/schemas/`、`backend/app/main.py`、`backend/app/config.py`、`backend/requirements.txt`、`backend/tests/` 下的公共测试、`contracts/`、`deploy/`、`docs/`、`.github/`、根目录文件。踩坑记录写 `deploy/NOTES.md`。

## 4. 要做的事

### 4.1 环境

1. 按 `docs/05-服务器与环境.md` 配好 SSH（`ssh kernel-eval` 能登录）。
2. 本地：`cd backend && pip install -r requirements.txt && python -m pytest -q`，31 个通过。
3. 了解部署：`bash deploy/deploy.sh`（默认部署 origin/main；`REF=HEAD bash deploy/deploy.sh` 部署本地当前提交）。**服务器连不上 GitHub**，所以只能从自己电脑打包推过去，不能在服务器上 git pull。
4. 服务器配置文件 `/opt/kernel-eval/kernel-eval.env`（改完 `sudo systemctl restart kernel-eval`）；日志 `journalctl -u kernel-eval -n 100`。

### 4.2 CI

`.github/workflows/ci.yml` 已写好（Python 3.12，装依赖，`cd backend && python -m pytest -q`）。第一次推到 GitHub 后确认 Actions 跑绿；在仓库设置里给 main 加分支保护：必须 PR、必须 CI 通过。

### 4.3 阶段 1 关卡：真实智能体（和块 5 一起）

块 5 建好 Dify 应用、把 `app-` 开头的应用密钥私聊给你后：

1. 改服务器 `/opt/kernel-eval/kernel-eval.env`：
   ```text
   KE_MOCK_MODULES=ingest,buildrun,analyze,diff,scoring
   KE_DIFY_APP_KEY=app-…
   ```
   重启服务。这样只有智能体是真实的，其余用样例 1 的固定结果，工程目录里是上传的真实代码。
2. 上传样例 1（服务器 `/data/kernel-eval/samples/样例1_完整工程`，打成 zip；可以在 <http://132.232.242.186/docs> 里上传），开始评测，轮询到 done。
3. 按块 5 任务说明第 4.4 节的表检查。
4. **确认 Dify 客户端**（`core/dify_client.py`）：抓一次原始事件流（`curl -N` 调 `http://127.0.0.1:8080/v1/chat-messages`，或在 `chat()` 里临时打日志），确认 Dify 1.17.1 的 `agent_thought`、`agent_message`、`message_end` 字段和代码一致，知识库检索的工具名以 `dataset_` 开头。不一致就改客户端，**接口不变**。
5. 确认追问可行。agent 切成真实后 followup 也会用真实实现，块 6 做完之前调 `/followup` 会返回“还没实现”，这是正常的。这一关只需要用 `curl` 带上报告里的 conversation_id 和 `user=task-<任务号>` 直接调 Dify 再发一条消息，能接着上下文回答即可。

过关标准：样例 1 走到 done，工具记录里 source=agent 有 compile_project、run_kernel、clang_scan、read_source 和至少一条 knowledge；同一会话能继续对话。

### 4.4 切真实模块（阶段 2–3）

各块的模块合进 main、在服务器上自己测过以后，逐个从 `KE_MOCK_MODULES` 里去掉：

| 顺序 | 去掉 | 前提 | 切完检查 |
|---|---|---|---|
| 1 | ingest、diff | 块 2 完成 | 4 份样例上传后工程列表对（样例 2 是 11 个）；样例 1 对比结果 same 14 / modified 26 / added 10 |
| 2 | buildrun | 块 3 完成 | 样例 1 编译通过、运行出提示符；lab6_pro 是 EXC_STORM |
| 3 | analyze | 块 4 完成 | 样例 1 扫描 14/15、7 条告警 |
| 4 | scoring | 块 6 评分完成 | 样例 1 总分合理，报告页正常 |

每切一个，用样例 1 完整跑一遍，有问题回滚这一项（加回去）并通知对应块。全部切完后 `KE_MOCK_MODULES=` 为空。

### 4.5 模型选定

默认一直用 `deepseek/deepseek-flash`。块 5 做了模型对比（选做）并决定换成 `glm-5.3-flash` 时，按结论改 Dify 应用的模型和服务器的 `KE_MODEL_NAME`（两边必须一致，后者只写进报告）。

### 4.6 部署与合并

- 审 PR：CI 绿、只改了自己块的目录（docs/04 第 1 节）、没有密钥和样例代码（看 diff 里有没有 `sk-`、`app-`、`BEGIN OPENSSH`、往届学生姓名）、没改 schemas/examples/别人的测试。
- 合并后部署：`git pull && bash deploy/deploy.sh`。部署脚本会保留上一版（`/opt/kernel-eval/previous`），出问题可以手工切回。
- 改 schemas 或示例：按 docs/02 第 10 节，先在群里说，改完同步改 `contracts/examples/` 和测试，通知所有人。

### 4.7 稳定性（阶段 3–4）

- 正常样例单次评测 ≤10 分钟（S4）：看 tool_calls 里每步 duration_ms，慢的找对应块。各步都有硬上限（编译 180 秒、运行 60 秒、扫描 300 秒、智能体总共 `KE_AGENT_TIMEOUT_S` 600 秒、读源码最多 `KE_READ_SOURCE_MAX` 20 次），出问题时任务会失败结束，不会一直卡在队列里。追问总预算 `KE_FOLLOWUP_TIMEOUT_S`（60 秒）。
- 服务器内存：Dify 占约 3G，同时只评一个任务（单线程队列已保证）。`free -h`、`docker stats` 看一眼。
- 磁盘：任务数据在 `/data/kernel-eval/tasks/`，演示前清一下旧任务。
- 演示前一天冻结 main，只修 bug。
