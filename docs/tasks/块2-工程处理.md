# 块 2：工程处理（含创新点 C）

> 给负责本块的同学和他的 AI 看。先读仓库根目录 `AGENTS.md`，再读本文。接口细节以 `docs/02-接口规范.md` 和 `backend/app/schemas/ingest.py` 为准。

## 1. 目标

把用户上传的东西变成干净的工程目录，并提供读源码和“学生改了什么”两项能力：

1. **整理上传**：解压 zip（或接收零散 .c/.h），过滤无关文件，识别出一个或多个工程。
2. **文件清单、读源码**：给智能体和网页用。
3. **创新点 C**：和参考实验代码对比，找出学生修改和新增的文件及行范围。

## 2. 范围

- 只改 `backend/app/ingest/` 和 `backend/tests/ingest/`，以及 `backend/app/ingest/NOTES.md`（踩坑记录）。
- 不改 `schemas/`、`contracts/`、`core/`。发现接口不够用，在群里提。
- 纯 Python 标准库就能做完（zipfile、pathlib、difflib），不需要 Docker，Windows 上就能开发。

## 3. 要实现的函数（签名冻结，在 `backend/app/ingest/__init__.py`）

```python
class PathInvalidError(ValueError): ...
def ingest_upload(task_dir: Path, upload_paths: list[Path], upload_name: str) -> IngestResult
def list_files(project_dir: Path, project_id: str) -> FileList
def read_source(project_dir: Path, path: str, start_line: int, end_line: int) -> SourceSlice
def diff_reference(project: Project, project_dir: Path, ref_root: Path) -> DiffResult
def change_flags(diff: DiffResult | None, path: str, line: int) -> tuple[bool | None, bool]
```

可以在 `ingest/` 下拆多个文件，但 `__init__.py` 必须导出这 5 个函数和 `PathInvalidError`。示例输出：`contracts/examples/ingest_result.json`、`file_list.json`、`source_slice.json`、`diff_result.json`。`app/core/mocks.py` 里有一个很粗糙的假实现可以参考接口用法（不要照抄它的逻辑，它没做安全检查）。

## 4. 详细要求

### 4.1 ingest_upload

输入：`task_dir/upload/` 下已经保存好的文件（一个 zip，或 1–50 个 .c/.h），块 1 已检查过扩展名和 20MB 上限。

**解压安全**（违反任何一条返回 status=failed，不抛异常）：

| 情况 | error.code |
|---|---|
| zip 损坏、加密 | UPLOAD_BAD_ZIP |
| 条目是绝对路径、含 `..`、是符号链接 | UPLOAD_UNSAFE_PATH |
| 解压后总大小 > `config.UNPACK_MAX_BYTES`（100MB）或文件数 > `config.UNPACK_MAX_FILES`（5000） | UPLOAD_TOO_LARGE（边解压边累计，超了立即停） |
| 过滤后一个 .c 文件都没有 | NO_SOURCE_FOUND |

**中文文件名**：Windows 打的 zip 文件名通常是 GBK，但没设 UTF-8 标志位（flag bit 11）。没设标志位时，把 zipfile 给出的名字 `name.encode("cp437")` 后先试 `decode("utf-8")`，失败再 `decode("gbk")`。样例 1 里有 `创新功能实现.md`，必须解出正确名字。

**过滤**（被过滤的计入 ignored_count）：

- 目录：`.git`、`__MACOSX`、`.vscode`、`.idea`、`build`、`cmake-build-*`、`node_modules`
- 文件：`.DS_Store`、`Thumbs.db`、`*.o`、`*.obj`、`*.a`、`*.so`、`*.elf`、`*.bin`、`*.img`、`*.exe`、`*.dll`、`*.map`、`*.zip`、`*.rar`、`*.7z`、`*.tar*`
- 任何 > 1MB 的文件

解压结果放 `task_dir/unpacked/`。

**识别工程**（在 unpacked/ 里找）：

1. 一个目录 X 如果满足 `X/src/CMakeLists.txt` 存在，或者 `X/CMakeLists.txt` 存在且包含 `project(`，就是一个完整工程（kind=full）的根。
2. 已经是工程根的目录，它的子目录不再当工程根（样例 1 的 `src/` 不能被单独识别）。
3. 一个工程都没找到时，把所有 .c/.h 当成**一个**片段工程（kind=fragment），根取所有 .c 文件的公共父目录。
4. 工程根下的全部文件拷贝到 `task_dir/projects/{project_id}/`（保持相对路径）。不在任何工程里的文件忽略。

**工程字段**：

| 字段 | 规则 |
|---|---|
| project_id | 按工程根路径字典序 p1、p2… |
| name | 工程根目录名；工程根就是解压根时用 upload_name 去掉扩展名 |
| root | 相对 unpacked/ 的路径，根本身写 `.` |
| arch | 工程内 CMakeLists、.S、.ld、.c 里出现 `aarch64`/`armv8`/`cortex-a` → aarch64；出现 `riscv` → riscv64；否则 unknown |
| buildable | kind=full 且 arch=aarch64 |
| has_run_script | 工程根下有 `runMiniEuler.sh` |
| file_count、c_files | 工程内文件数、.c 文件数 |
| note | 给人看的补充，如“只有代码片段，无法编译运行” |

**四份样例的预期**（必须写成测试）：

| 样例 | 工程数 | kind | arch | 备注 |
|---|---|---|---|---|
| 样例 1 | 1 | full | aarch64 | 50 个文件、15 个 .c，有运行脚本 |
| 样例 2 | 11 | full | aarch64 | lab1、lab2、lab2_hw1、lab4、lab5、lab5_pro、lab6、lab6_pro、lab8、lab9、lab10 |
| 样例 3 | 1 | fragment | riscv64 | buildable=false |
| 样例 4 | 1 | full | aarch64 | |

测试时把样例目录临时打成 zip 再调 ingest_upload；样例从 `config.SAMPLES_ROOT` 找，找不到就 `pytest.skip`。也要测“直接上传 3 个 .c 文件”、“zip 里有 `../evil.c`”、“zip 损坏”、“GBK 文件名”。

### 4.2 list_files

工程内全部文件，按路径排序。`lines` 按 `\n` 计（文件末尾没有换行也算一行；空文件 0 行），`lang` 按扩展名：.c→c、.h→h、.s/.S→asm、CMakeLists.txt 和 .cmake→cmake、.sh→shell、.ld/.lds→ld、.md→markdown、其他 other。

### 4.3 read_source

- path 必须在工程内：拼出来的绝对路径 `resolve()` 后必须在 project_dir 之下，不能是目录、不能不存在，否则抛 `PathInvalidError`。含 `..`、绝对路径、反斜杠都要拒绝或规范化后再判断。
- 二进制文件（含 `\x00`）抛 PathInvalidError。
- 读取用 `utf-8`，失败的字节替换（`errors="replace"`）；`\r\n` 当一个换行。
- `start_line < 1` 当 1；`end_line` 超过文件末尾截到末尾；一次最多 200 行（`end_line = min(end_line, start_line + 199)`）；`start_line` 超过末尾抛 PathInvalidError。
- `text` 每行格式 `f"{行号:>5} | {内容}"`，用 `\n` 连接；`evidence_id` 返回空串（块 1 分配）。

### 4.4 diff_reference（创新点 C）

参考仓库在 `ref_root`（服务器 `/data/kernel-eval/ref/os2024_exp_redo_kp`，本地解压 `ref-labs.tar.gz` 得到），下面是 `lab1`、`lab2`、`lab4`、`lab5`、`lab6`、`lab7`、`lab8`、`lab10` 等目录，**每个 lab 目录的结构和学生工程根一致**（都有 `src/`）。

1. `ref_root` 不存在或下面没有 lab 目录 → status=unsupported，note 说明原因。
2. 对每个 lab，统计学生工程和它**同相对路径的文件数**，写进 candidates。
3. 基线选同路径文件最多的 lab，并列取编号大的（lab10 > lab8，按数字比，不按字符串比）。全部为 0 → unsupported。
4. 逐个学生文件比较（只比文本文件），比较前每行去掉 `\r` 和行尾空白，去掉文件末尾的空行：
   - 基线里没有这个路径 → added，hunks = `[{start:1, end:行数}]`，added_lines = 行数
   - 内容相同 → same
   - 不同 → modified，用 `difflib.SequenceMatcher(None, ref, stu, autojunk=False)` 的 opcodes：`replace`/`insert` 的学生侧行范围 `[j1+1, j2]` 记入 hunks 并累加 added_lines；`replace`/`delete` 的参考侧行数累加 removed_lines。只删除没新增的文件 hunks 为空。
5. evidence_id：按路径排序，只给 modified/added 依次编 D1、D2…；same 为空串。files 包含全部学生文件（含 same）。
6. ref_commit 填 `config.REF_COMMIT`；ref_repo 用默认值。

**必须对上的数**（写成测试，样例或参考代码不存在时 skip）：

- 样例 1 → baseline lab10，same 14、modified 26、added 10，candidates `{"lab1":7,"lab2":9,"lab4":11,"lab5":19,"lab6":32,"lab7":37,"lab8":39,"lab10":40}`；`src/shell/shmsg.c` 是 added，`src/bsp/vsnprintf_s.c` 是 same，`src/main.c` 的 hunks 包含第 56–57 行
- 样例 4 → baseline lab10，same 49、modified 9、added 3（共 61 个文件、19 个 .c）
- 样例 3（RISC-V 片段）→ unsupported 或 candidates 全 0，不能报错

和 `contracts/examples/diff_result.json` 逐字段比对（样例 1）。

### 4.5 change_flags

```text
diff 为 None 或 status != "passed"        → (None, False)
path 不在 diff.files 里                   → (None, False)
文件 change == "same"                     → (False, True)
modified / added：line 落在任一 hunk 里    → (True, False)，否则 (False, False)
```
