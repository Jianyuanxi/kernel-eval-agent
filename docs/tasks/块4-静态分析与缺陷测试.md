# 块 4：clang 静态分析（含创新点 A 植入缺陷测试）

> 给负责本块的同学和他的 AI 看。先读仓库根目录 `AGENTS.md`，再读本文。接口细节以 `docs/02-接口规范.md` 第 7 节、`docs/03-评分规则.md` 第 8 节和 `backend/app/schemas/analyze.py` 为准。

## 1. 目标

1. **clang 扫描**：对工程里每个 .c 文件跑 `clang --analyze`，把告警整理成带编号（C1、C2…）、带缺陷类型的结构化结果。这是任务原文“调用 clang 静态分析工具扫描”的核心。
2. **创新点 A**：在样例里人为植入 10 个已知缺陷，统计“只用 clang”和“完整系统（clang + 智能体）”各检出几个，证明智能体有用。

## 2. 范围

- 只改 `backend/app/analyze/`、`backend/tests/analyze/`、`evaluation/`，踩坑记录写 `backend/app/analyze/NOTES.md`。
- 沙箱执行器用块 3 的 `app.buildrun.sandbox`（`run_in_sandbox`、`prepare_workspace`），不要自己再写一套 docker 调用；需要改它找块 3。
- 需要 Docker：本机 WSL2，或服务器（`bash deploy/devsync.sh 你的拼音名`，见 docs/05 第 4 节）。镜像 `kernel-eval-sandbox:0.1` 里已有 clang 18.1.3。

## 3. 要实现的函数（签名冻结，在 `backend/app/analyze/__init__.py`）

```python
def scan(project: Project, project_dir: Path, work_dir: Path, log_dir: Path) -> ScanResult
```

示例输出：`contracts/examples/scan_result.json`（样例 1 的真实结果：14/15 个文件，7 条告警）。

## 4. 详细要求

### 4.1 完整工程（project.kind == "full"）

1. `prepare_workspace(project_dir, work_dir)` 拷贝工程并改写工具链路径。
2. 在沙箱里**只做 cmake 配置**拿 `compile_commands.json`（不要求编译成功）：
   ```text
   cmake -S src -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
   ```
   （没有 `src/CMakeLists.txt` 时用 `-S .`。）配置失败或没生成 compile_commands.json → 退回第 4.2 节的片段方式扫，ScanResult.mode 仍填 full。
3. 解析 compile_commands.json，**只取工程内的 .c 文件**（`.S` 汇编不扫）。每个文件从它的 command/arguments 里保留 `-I`、`-D`、`-include`、`-std=`、`-isystem` 参数（含分开写的 `-I path` 形式），其余（`-mcpu`、`-O2`、`-Werror` 等 gcc 参数）丢掉。
4. 每个文件单独执行（一个沙箱里用 shell 循环跑完全部文件也可以，总超时 `config.SCAN_TIMEOUT_S`）：
   ```text
   clang --analyze --target=aarch64-none-elf -ffreestanding -fno-builtin \
     -Wno-error=implicit-function-declaration -Wno-error=implicit-int -Wno-error=int-conversion \
     -Wno-error=incompatible-pointer-types -Wno-error=incompatible-function-pointer-types \
     -Xclang -analyzer-output=plist -o out/<序号>.plist <保留的参数> <文件>
   ```
   可以额外加 `-Xclang -analyzer-checker=alpha.security.ArrayBoundV2`（docs/03 第 8 节已有映射）。不要加别的检查器。
5. 某个文件 clang 退出码非 0 且没产出 plist → 记进 `files_failed`，reason 取 stderr 里第一条 `error:` 行（样例 1 的 `prt_sched_single.c` 会报 `conflicting types for 'OsMainSchedule'`）。
6. **解析 plist**（Python 标准库 `plistlib`）：每个 `diagnostics` 条目取 `check_name`、`description`、`location.line`、`location.col`、`location.file`（是 `files` 数组下标）。路径转成相对工程根（去掉 `/workspace/` 前缀）；不在工程内的（系统头文件）丢掉。
7. **去重**：(path, line, checker) 相同的只留一条。按 (path, line) 排序后编号 C1、C2…；`findings_total` 是去重后总数，`findings` 最多保留前 100 条。
8. **类型映射**：按 docs/03 第 8 节的表，按顺序第一条命中为准，填 `defect_type`；`severity` 按 `app.schemas.DEFECT_TYPES[defect_type][1]`；映射不到两个都为 null。`in_baseline_unchanged` 保持 null（块 1 填）。
9. `files_total` = 工程内 .c 文件数，`files_scanned` = 成功产出 plist 的文件数，`coverage = round(files_scanned / files_total, 2)`。
10. status：files_scanned ≥ 1 → passed；= 0 → unsupported。
11. 每个文件的命令、退出码、stderr 依次写进 `log_dir/scan.log`，`log_file` 填它的路径。
12. docker 起不来抛的 SandboxError **不要捕获**。

### 4.2 代码片段（project.kind == "fragment"）

- 先 `prepare_workspace(project_dir, work_dir)` 拷一份工作副本（沙箱只挂载 work_dir，看不到 project_dir），源文件和 `-I` 路径都用工作副本里的 `/workspace/...` 路径。
- 不跑 cmake。每个 .c 单独扫，参数用 `-I /workspace` 加上片段里每个含 .h 的目录（同样写成 `/workspace/...`）；`--target` 按 project.arch：aarch64 → `aarch64-none-elf`，riscv64 → `riscv64-unknown-elf`，unknown → 不加 target。
- 缺头文件扫不了的记进 files_failed。**一个都扫不成就是 unsupported，不能当作“零缺陷”。**
- 样例 3 预期：unsupported，coverage 0（docs/02 第 7 节已验证）。

### 4.3 告警说明（可选）

给 `message` 保留 clang 原文（英文）。不需要翻译，智能体会解释。

## 5. 创新点 A：植入缺陷测试

### 5.1 测试集

在**样例 1 和样例 4** 上人为改代码，植入 10 个缺陷，每个缺陷一个独立补丁（每次只植入一个，评一次）。类型要覆盖不同难度：

| 至少要有 | 例子 |
|---|---|
| clang 能扫出来的 3 个以上 | 空指针解引用、除零、未初始化变量 |
| clang 扫不出、要读代码才能发现的 3 个以上 | 共享变量不加锁（关中断）、信号量 P/V 不配对、中断处理里调用会阻塞的函数、栈申请后出错分支没释放 |
| 和操作系统知识点强相关的 | 任务切换没保存某个寄存器、定时器中断没清中断标志 |

- `evaluation/truth.yaml`（进仓库）：每条写 `id`、`sample`（样例目录名：`样例1_完整工程` 或 `样例4_完整工程`）、`patch`（补丁文件名）、`path`、`line`、`type`（24 个缺陷类型代码之一）、`description`、`clang_expected`（预期 clang 能不能扫出），可选 `accept_types`（也算对的等价类型）。
- 补丁放 `evaluation/patches/*.patch`，**不进仓库**（已在 .gitignore；补丁里有样例代码）。统一上传到服务器 `/data/kernel-eval/evaluation/patches/`，组里共享。
- 每个补丁要保证工程还能编译通过（否则编译与运行、功能两项都 0 分，测不出缺陷检出）。

### 5.2 统计脚本 `evaluation/run_eval.py`

```bash
python evaluation/run_eval.py --base http://127.0.0.1:8000 --samples /data/kernel-eval/samples \
  --patches /data/kernel-eval/evaluation/patches --truth evaluation/truth.yaml --out evaluation/result.md
```

先把**没打补丁**的样例 1、样例 4 各评一次，存成基线报告。然后对每个植入缺陷：拷贝样例 → `git apply`（或 `patch -p1`）→ 打 zip → 调 `/api/tasks` 上传、`/start` 开始、轮询到 done → 取报告。判定（只看基线报告里**没有**的条目，避免把样例原有的问题算成检出）：

- **clang 检出**：`report.scan.findings` 里有同文件、行号差 ≤3、`defect_type` 与 truth 相同的新告警
- **系统检出**：`report.defects` 里有同文件、行号差 ≤3、`type` 与 truth 相同的新缺陷。确实存在等价类型的（例如关中断未恢复也可以报成 RACE），在 truth.yaml 该条加 `accept_types: [RACE]` 逐条列出，不用整个知识点分类代替

输出 Markdown 表：每个缺陷一行（id、类型、clang 检出、系统检出、报告里的标题），最后一行合计检出率。验收要求（docs/06 S8）：**完整系统至少检出 6 个**，同时给出只用 clang 的数字做对比。结果表进仓库（`evaluation/result.md`，只有编号和统计，不含样例代码）。
