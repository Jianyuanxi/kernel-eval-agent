## 1. 目标

1. **网页**：上传 → 选工程 → 看评测进度和工具调用过程 → 看报告 → 导出 → 追问。任务原文的“文件上传、结果输出、演示智能体工具调用能力”都靠它展示。

3. **创新点 B 追问**：在报告页就某条缺陷继续问智能体，复用评测时的会话。
4. **一键验收脚本**：跑 docs/06 的 S1–S11。

这一块活最多，前端和后端可以分开先后做：第 1 周先做评分（纯 Python，最容易测）和前端骨架。

## 3. 后端：要实现的函数（签名冻结）

```python
# backend/app/scoring/__init__.py
def compute_score(project: Project, build: BuildResult | None, run: RunResult | None,
                  review: ReviewResult, defects: list[ReportDefect]) -> ScoreResult
def render_markdown(report: Report) -> str

# backend/app/followup/__init__.py
def answer_followup(report: Report, req: FollowupRequest, dify: DifyClient) -> FollowupResponse
```

### 3.1 compute_score

完全按 docs/03 第 1–6 节。要点：

- mode：`project.buildable` 为 true 是 full，否则 fragment
- compile_run：fragment → null；build 或 run 的 status=error → null；build failed → 0；build passed → 10 − 警告扣分 +（run passed ? 10 : 0）
- features：完整工程 build failed → 0（不看模型判断）；否则 done 5 / partial 2.5 / none 0 相加
- reliability：遍历 defects，`in_baseline_unchanged=true` 的 `counted=False` 不扣，其余 `counted=True` 并按 `SEVERITY_PENALTY[defect.severity]` 扣，记进 deductions；最低 0
- style：good 15 / medium 10 / poor 5
- total、grade：docs/03 第 6 节公式。注意 `int(x + 0.5)`，不要用 Python 的 `round()`（78.5 会变成 78）
- 每项 reasons 写中文原因，格式参考 `contracts/examples/score_result.json`

**必须有的测试**（`backend/tests/scoring/`，纯函数，不需要 Docker）：

| 用例 | 预期 |
|---|---|
| 用 contracts/examples 里样例 1 的 build/run/review 和 report.defects | 和 `score_result.json` 完全一致（79 中等，raw_total 78.5，deductions 4 条） |
| build failed | compile_run 0、features 0 |
| build status=error | compile_run null，按剩下三项 /80 折算 |
| fragment（build、run 都是 None） | compile_run null，/80 折算 |
| 警告 0 / 1 / 10 / 11 条 | 编译分 10 / 9 / 9 / 8 |
| 缺陷扣到负数 | reliability 0 |
| 全部 in_baseline_unchanged | reliability 25，counted 全 false |
| 边界 89.5 / 90 / 79.99 | total 90 / 90 / 80，等级对应 |
| 同样输入跑两次 | 结果相同 |

### 3.2 render_markdown

导出的 Markdown 至少包含：标题（工程名、任务号、生成时间）、总分和等级、四项分数表（项、得分/满分、原因）、8 个功能点表、缺陷清单（每条：级别、类型中文名、`path:line`、标题、描述、知识点、建议、改前改后代码块、是否计分）、规范与创新评价、工具调用过程表（seq、来源、工具、状态、摘要）、warnings。`score=null` 的项显示“不计分”。测试：用 `contracts/examples/report.json` 生成，检查以 `#` 开头、包含“79”“中等”、包含每条缺陷的 `path:line`。

### 3.3 answer_followup（创新点 B）

```text
1. user = f"task-{report.task_id}"，conversation_id = report.conversation_id（必须和评测时相同，否则 Dify 认不出会话）
2. defect 文本：req.defect_index 为 None → "（未指定）"；否则取 report.defects[i]，拼成
   "[{severity}] {type_name} {path}:{line} {title}"
3. query = prompts.render("followup", task_id=…, project_id=report.project.project_id, defect=…, question=req.question)
4. before = 当前工具记录条数（storage.read_tool_calls(task_id) 的最大 seq）
5. res = dify.chat(query, user, conversation_id)
6. res.thoughts 里 tool 以 "dataset_" 开头的，每条用 storage.append_tool_call 补一条
   {source:"followup", tool:"knowledge", status:"passed", summary:"检索知识库：…"}（格式参考 core/pipeline.py 的 _record）
7. tool_calls = storage.read_tool_calls(task_id, before)（追问期间智能体调我们的工具时，工具接口已经自动记成 source=followup）
8. 返回 FollowupResponse(answer=res.answer.strip(), tool_calls=…)
```

**不改报告、不重新计分。** DifyError 不要捕获（`api.py` 会转成 502）。测试：写一个假的 DifyClient（有 `chat` 方法、返回固定 ChatResult）传进去，检查 user、conversation_id、query 里有缺陷标题、报告文件没被修改。

## 4. 前端

技术栈：**Vue 3 + Vite + JavaScript**（不用 TypeScript），图表用 **ECharts**，组件库可选 Element Plus。`package-lock.json` 必须提交（服务器用 `npm ci` 构建，npm 源已设成 npmmirror）。

### 4.1 本地开发

```bash
# 终端 1：后端，全部假数据
cd backend && python -m uvicorn app.main:app --reload --port 8000      # backend/.env 里 KE_MOCK_MODULES=all
# 终端 2：前端
cd frontend && npm install && npm run dev
```

`vite.config.js` 里把 `/api` 代理到 `http://127.0.0.1:8000`。所有请求都用相对路径 `/api/...`（部署后 nginx 同域转发，不要写死 IP）。

假数据模式下上传任何 zip 都会得到样例 1 的报告（79 分），可以直接开发报告页。要测真实评分：`KE_MOCK_MODULES=ingest,buildrun,analyze,diff,agent`（只有 scoring 是你的真实代码）。

### 4.2 页面

| 页面 | 内容 | 用到的接口 |
|---|---|---|
| 上传 | 拖拽或选择一个 .zip，或多个 .c/.h；显示大小限制（20MB）；出错按 `error.code` 显示中文提示 | `POST /api/tasks` |
| 选工程 | 列出识别出的工程（名称、类型、架构、文件数、能否编译、备注）；只有一个时自动开始 | `POST /api/tasks/{id}/start` |
| 进度 | 阶段条（编译 → 运行 → 扫描 → 对比 → 智能体评审 → 评分）、当前 progress 文字；**工具调用时间线**：每 2 秒请求一次 events，只取新记录（`after=已有最大 seq`），按来源着色（流水线/智能体/追问），显示工具名、状态、耗时、摘要；done 后跳报告页，failed 显示 error | `GET /api/tasks/{id}/events?after=N` |
| 报告 | 见 4.3 | `GET /api/tasks/{id}/report` |

任务号放进 URL（如 `/#/task/t2026…`），刷新页面能恢复。

### 4.3 报告页（docs/06 S12 逐项要有）

- 顶部：总分、等级、工程名、模型、生成时间；**雷达图**（四项得分率，null 的项不画）；导出 JSON / Markdown 按钮（`GET /api/tasks/{id}/export?format=json|md`）
- 四项分数卡片：得分/满分、reasons
- 编译运行：状态、警告数、诊断列表（可展开 log_tail）；运行输出（boot_output、每条命令及输出，等宽字体）；片段模式显示“只提交了代码片段”
- 8 个功能点：状态标签（完成/部分/未完成）、理由、代码位置（点击打开源码）
- 缺陷清单：按级别排序；每条显示级别标签、类型中文名、`path:line`（点击打开源码并高亮该行）、标题、描述、来源（clang/gcc/llm…）、知识点分类和讲解、修改建议、改前/改后代码对比；`in_baseline_unchanged` 显示“参考代码原有，不扣分”，`in_student_change` 显示“学生改动”；每条有“追问”按钮
- 规范、创新评价
- 参考代码对比（创新点 C）：基线 lab、相同/修改/新增数量、修改和新增文件列表
- 工具调用过程：完整时间线（同进度页）+ 智能体思考过程（agent_thoughts 可折叠）
- warnings（如果有）
- 源码查看器：抽屉或弹窗，调 `GET /api/tasks/{id}/source?path=&start=&end=`，每次最多 200 行，可以上下翻页
- 追问框：选中某条缺陷或自由提问，`POST /api/tasks/{id}/followup`，显示回答（Markdown 渲染，可用 marked）和这次追问的工具调用；等待时显示加载状态（最长约 1 分钟）
