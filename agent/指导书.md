# 智能体与知识库（块 5）

本章说明如何在 Dify 中搭建内核代码评测智能体：自定义工具、操作系统知识库、Agent 应用，以及提示词与后端工具预算的对齐方式。块 5 **不打分**；智能体只输出符合 `ReviewResult` 的 JSON，分数由块 6 计算。仓库侧“源码”全部在 `agent/`，线上配置改完后必须导出 DSL 再提交，才算进仓库。

| 路径 | 内容 |
|---|---|
| `agent/prompts/` | 系统指令与后端模板（`system.md`、`nudge.md`、`repair.md`、`review_query.md`、`followup.md`） |
| `agent/knowledge/` | 知识库 Markdown 原文（10 份） |
| `agent/dsl/kernel-eval-agent.yml` | 从 Dify 导出的应用 DSL（不含密钥） |
| `agent/README.md` | 约 15 分钟从零重建步骤 |
| `agent/NOTES.md` | 踩坑与阶段记录 |

提示词里的 `{task_id}`、`{project_id}` 等占位符由 `backend/app/core/prompts.py` 填充，**名字不能改、不能删**；文件开头的 `<!-- -->` 注释会被去掉，不会发给模型。粘贴到 Dify「指令」时也必须去掉该注释，否则会进线上配置。

## 2. 自定义工具 `kernel_eval_tools`

1. 集成 → 工具 → **Swagger API 作为工具**（或等价「自定义」入口）→ 创建。
2. 名称：`kernel_eval_tools`。
3. Schema：粘贴仓库 `contracts/tools.openapi.yaml` 全文；`servers.url` 保持公网地址。
4. 鉴权：API Key，类型为自定义请求头；键名 `X-Tool-Token`；值为上一节的工具令牌。
5. 保存后应出现 6 个工具：`list_files`、`read_source`、`compile_project`、`run_kernel`、`clang_scan`、`diff_reference`。
6. 用服务器已有任务的 `task_id`（`ls /data/kernel-eval/tasks/`）测一次 `list_files`，确认鉴权与公网可达。

### 踩坑：`provider_id` 必须是 UUID

Agent 应用绑定工具时，配置里的 `provider_id` 必须是自定义工具的 **UUID**（例如导出 DSL 里可见的 `13dedd27-…`），不能填名字 `kernel_eval_tools`。填名字会导致 Postgres 报 `invalid input syntax for type uuid`，对话直接 500。手工搭应用或改 DSL 后都要核对这一点。

## 3. 知识库 `os-knowledge`

### 3.1 文档要求

在 `agent/knowledge/` 按知识点各写一份 Markdown（自己总结，勿整段复制教材）。每类缺陷以 `## 缺陷类型代码 中文名` 起节，便于按 `\n## ` 切段。覆盖关系见任务说明表：`K_MEM`、`K_ADDR`、`K_SYNC`、`K_CRIT`、`K_IRQ`、`K_CTX`、`K_SYSCALL`、`K_DEV`、`K_GENERAL`，以及 `MiniEuler-实验要点.md`（8 个功能点一般落在哪些文件/函数）。

**禁止**在知识库写往届样例的具体缺陷位置或“标准答案”；只写通用原理与 MiniEuler / ARM64 常见写法（例如关中断后每个返回分支都要恢复中断）。

### 3.2 在 Dify 中创建

1. 知识库 → 创建即用型 → 名称 `os-knowledge`。
2. 上传上述 10 份 Markdown。
3. 分段：自定义，分隔符 `\n## `，最大长度 800。
4. 索引：高质量；向量模型 `kinfra-text-embedding-0.6b`。
5. 检索：混合检索；语义 0.7 / 关键词 0.3；Top K 4；不开重排（TokenHub 无重排模型）。

### 踩坑：向量库环境

高质量索引依赖 pgvector。若报 `PGVECTOR_PASSWORD` 相关错误，检查服务器 `/opt/dify/docker/envs/vectorstores/pgvector.env` 是否存在且含 `PGVECTOR_HOST=pgvector` 等项，再重启 Dify 的 `api` / `worker` / `worker_beat`（密码与 compose 默认一致即可）。组员不要擅自改 `/opt/dify/` 以外的部署；缺文件时找有权限的同学补。

知识库加在 Agent 的**上下文**里，不要做成工作流节点。后端从 Dify `agent_thought` 里识别名称以 `dataset_` 开头的工具，补一条 `knowledge` 调用记录。

## 4. Agent 应用 `kernel-eval-agent`

1. 工作室 → 创建应用 → **Agent**（不要选 Chatflow / 工作流），名称 `kernel-eval-agent`。
2. 模型：`deepseek/deepseek-flash`；Agent 策略：**函数调用（Function Calling）**；最大迭代 **20**。
3. 指令：粘贴 `agent/prompts/system.md`（去掉开头 HTML 注释）。
4. 工具：添加 `kernel_eval_tools` 的 6 个工具（再次确认 `provider_id` 为 UUID）。
5. 上下文：绑定 `os-knowledge`。
6. 关闭开场白与建议问题 → **发布**（改指令后不发布，API 仍用旧版）。
7. 访问 API → 创建密钥，私聊交给块 1。

也可导入 `agent/dsl/kernel-eval-agent.yml`，再检查工具鉴权、知识库绑定与模型，然后发布。

Agent 对话 API 只支持 `response_mode=streaming`，不支持 blocking。函数调用下模型可能一次并行调多个工具，后端会逐条记录，无需特殊处理。

## 5. 提示词要点（与后端行为对齐）

系统指令要求智能体：先列文件，完整工程再编译 / 运行 / clang / 对比参考；读源码确认后再写缺陷；最后只输出一个 JSON 代码块。更细的字段约束以 `backend/app/schemas/review.py` 为准。

调参时反复验证过的几条：

| 主题 | 做法 |
|---|---|
| 片段模式 | compile / run / clang 失败常见，**不要编造** B/R/C，也不要反复重试；无运行证据时功能点慎标 `done` |
| 读源码预算 | 评审阶段后端最多成功 `read_source` **20** 次，超过返回 `READ_LIMIT`；提示词要求优先读 clang 告警位置与 `diff_reference` 的 modified/added，收到 `READ_LIMIT` 后**禁止再读**，直接出最终 JSON |
| 缺陷数量 | 提示词约束 `defects` 最多 **20** 条（宁缺毋滥）；后端 schema 上限可以更宽，两者不冲突 |
| 类型写准 | 互相等待用 `DEADLOCK`；关中断后某返回路径未恢复用 `IRQ_NOT_RESTORED`；不要把严重问题随意降成 `OTHER_*` |
| 证据 | `evidence_ids` 只能引用工具真实返回的 B/R/C/D/S；位置必须来自读到的源码 |
| 基线问题 | 与参考代码相同的文件也可报，但要在 description 说明「参考代码原有」 |

后端在缺工具时会发一次 `nudge.md`，JSON 不合格会发一次 `repair.md`。追问模板 `followup.md` 由块 6 调用：直接回答、不超过约 300 字、可再读源码、**不改分数**。TokenHub 若出现 402「免费体验额度已耗尽」，需组长在控制台开通后付费后再验追问。

模型对比（`deepseek/deepseek-flash` vs `glm-5.3-flash`）为选做；未做则一直用 deepseek，换模型时通知块 1 改 `KE_MODEL_NAME`。

## 6. 导出 DSL 与仓库同步

每次在 Dify 改完应用并发布后：

1. 应用 → 导出 DSL（不要包含密钥）。
2. 覆盖保存为 `agent/dsl/kernel-eval-agent.yml`。
3. 自检：无 `app-` / 工具令牌；`pre_prompt` 含当前指令要点（如 `READ_LIMIT`、缺陷上限表述），且不含 `system.md` 开头注释。
4. 与 `agent/prompts/system.md`、必要时的 `NOTES.md` 一并提交。

只改 `agent/` 目录；不改后端、schemas、contracts。

## 7. 怎么验收这块

| 检查 | 说明 |
|---|---|
| 阶段 1 关卡 | 块 1 将 `KE_MOCK_MODULES` 设为除智能体外均 mock，并填好 `KE_DIFY_APP_KEY`；样例 1 跑到 `done`，agent 侧需有 compile / run / clang / 至少一次成功的 `read_source`、至少一次 knowledge；能指出样例 1 中 shell 消息处理附近的数组越界；`warnings` 里因格式丢弃的缺陷宜 ≤2 |
| 多样例 | 样例 1、4、样例 2 的 lab10 与 lab6_pro、样例 3 在真实模式下均能 `done`，必调工具与知识库检索齐全（对应验收 S7） |
| 植入缺陷 | 配合块 4 测试集，完整系统检出 ≥6（S8）；本块通过提示词与知识库提高可解释性与类型准确度，不改扫描代码 |
| 重建 | 他人按 `README.md` / 本章能在约 15 分钟内重建工具、知识库与应用 |

排错优先看：Dify 应用「日志与标注」、报告中的 `tool_calls` / `agent_thoughts`，以及是否忘记发布新指令。
