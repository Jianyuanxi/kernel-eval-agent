# 块 4：静态分析与植入缺陷测试指导书

## 1. 目标、接口和环境

本章说明如何扫描 MiniEuler 内核工程，并用已知缺陷比较 clang 与完整智能体系统的检出率。扫描入口为 `app.analyze.scan(project, project_dir, work_dir, log_dir) -> ScanResult`，调用方使用冻结的数据结构，无须额外调用模型。

环境为 Python 3.12、项目固定依赖，以及 `kernel-eval-sandbox:0.1` Docker 镜像（含 clang 18.1.3）。外部命令由块 3 的公共 `run_in_sandbox` 执行；不能在扫描模块中另建 Docker 调用链。样例、补丁、运行报告和密钥不提交到仓库。

## 2. 完整工程扫描

1. 用 `prepare_workspace` 创建工作副本并归一化工具链路径，保留原始工程。
2. 只执行 CMake 配置：`cmake -S src -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`。不存在 `src/CMakeLists.txt` 时使用工程根目录。配置失败或没有编译数据库时按片段参数回退，结果模式仍为 `full`。
3. 解析 `compile_commands.json`，仅扫描工程内的 C 文件。保留 `-I`、`-D`、`-include`、`-std=`、`-isystem`；相对路径按编译目录转换为沙箱工作副本路径，丢弃 GCC 专用选项。
4. 每个文件执行 `clang --analyze`，指定裸机目标、freestanding、plist 输出和规范中的诊断兼容选项。只在默认检查器外开启允许的数组边界检查器。
5. 用 `plistlib` 解析诊断，路径转换为工程内相对路径，过滤工程外文件。按评分规则第 8 节顺序匹配检查器，类型对应级别由 schemas 给定。
6. 按路径、行号、检查器去重，再按路径和行号排序编号 C1、C2……；保存总数，列表最多保留 100 项。命令、退出码和 stderr 写入 `scan.log`。

覆盖率为成功输出 plist 的文件数除以 C 文件总数。至少扫描成功一个文件返回 `passed`，全部失败返回 `unsupported`。逐项保留失败原因，不能把无法扫描解释为零缺陷；沙箱基础设施错误向调用方抛出。

## 3. 代码片段扫描与样例检查

片段不运行 CMake，先建立工作副本，将工程根和含头文件的目录加入搜索路径。目标按 `aarch64`、`riscv64` 设置，未知架构不指定 target。缺头文件导致全部失败时仍返回 `unsupported`。

服务器实测：

| 样例 | 扫描结果 | 成功文件 / 总文件 | 告警数 |
|---|---|---|---|
| 样例 1 | passed | 14/15 | 7 |
| 样例 3 | unsupported | 0 / 片段文件总数 | 无可用扫描结果 |
| 样例 4 | passed | 19/19 | 7 |

样例 1 的一个文件存在 `OsMainSchedule` 类型冲突，记录为扫描失败，其余文件仍正常统计。

## 4. 建立植入缺陷测试集

测试清单为 `evaluation/truth.yaml`，10 项分别覆盖空指针、除零、未初始化变量、共享 tick 竞态、关中断未恢复、寄存器上下文保存、中断长时间忙等、信号量唤醒缺失、定时器中断清除遗漏、shell 读偏移回绕。

每个补丁独立作用于原始样例 1 或样例 4，先验证 `git apply --check`，再单独在沙箱中编译。已有 10 个补丁均已验证可编译。补丁放在服务器 `/data/kernel-eval/evaluation/patches/`，清单只记录位置、类型和说明；不要把含样例源码的补丁加入 Git。

样例 1 使用 CRLF 行尾，制作补丁时须保留原始回车，否则 Linux 上可能无法应用。当前补丁均为等行数替换，因此可直接比较基线行号；未来增加插入或删除行的补丁时，应先实现基线行号映射。

## 5. 运行真实评测

先检查 `/api/health`，确认 `mock_modules=[]`。在自己的服务器目录执行：

```bash
cd ~/dev/kuaisi
/opt/kernel-eval/venv/bin/python evaluation/run_eval.py \
  --base http://127.0.0.1:8000 \
  --samples /data/kernel-eval/samples \
  --patches /data/kernel-eval/evaluation/patches \
  --truth evaluation/truth.yaml --out evaluation/result.md
```

脚本先评测两个未修改样例并保存基线，再依次复制原样例、应用单个补丁、压缩上传、启动任务、轮询完成并取得报告。每个任务独立运行；任何基线失败都应先排查，不能跳过基线直接计算检出率。

判定要求为同文件、距离植入行不超过 3 行、具体类型匹配。基线已有的同文件、同行、同类型问题被排除，不能依赖模型标题是否换词判断新增。有真正等价类型时须逐条在清单中列出 `accept_types`，不能用整个知识点分类替代类型。多个候选中优先展示最接近植入行的标题。

## 6. 创新点 A 的真实结果

2026-10-29 在全真实服务上完成两份基线和十份植入报告。完整记录与任务编号见 [result.md](result.md)。

| 编号 | 缺陷类型 | clang | 完整系统 |
|---|---|---|---|
| A01 | NULL_DEREF | 检出 | 检出 |
| A02 | DIV_ZERO | 检出 | 检出 |
| A03 | UNINIT_VAR | 检出 | 检出 |
| A04 | RACE | 未检出 | 检出 |
| A05 | IRQ_NOT_RESTORED | 未检出 | 未检出 |
| A06 | CONTEXT_SAVE | 未检出 | 检出 |
| A07 | IRQ_LONG_WAIT | 未检出 | 检出 |
| A08 | DEADLOCK | 未检出 | 未检出 |
| A09 | OTHER_SEVERE | 未检出 | 未检出 |
| A10 | OUT_OF_BOUNDS | 未检出 | 检出 |
| 合计 | 10 项 | 3/10（30%） | 7/10（70%） |

完整系统增加 4 个检出，检出率提高 40 个百分点，达到 S8“至少 6 个”的标准。A05 未报告目标问题；A08、A09 有对应问题描述，但模型给出不同类型，严格规则下均未计入。统计没有为达标而追加泛化等价类型。

该结果来自固定的 10 项测试集及一次真实评测，不代表所有操作系统缺陷的普遍识别能力。模型生成具有波动性，重跑结果应按同样规则重新记录。

## 7. 验证与常见问题

服务器测试应显式设置样例和参考目录，并要求真实沙箱：

```bash
cd ~/dev/kuaisi/backend
KE_REQUIRE_SANDBOX=1 KE_DATA_ROOT=/tmp/ke-kuaisi \
KE_REF_ROOT=/data/kernel-eval/ref/os2024_exp_redo_kp \
KE_SAMPLES_ROOT=/data/kernel-eval/samples \
/opt/kernel-eval/venv/bin/python -m pytest -q
```

扫描测试覆盖参数提取、plist 解析、全部映射规则、去重编号、片段空指针和样例 1/3/4。统计回归测试覆盖基线过滤、等价类型白名单、标题换词、邻近新缺陷和表格转义。

- 沙箱仅挂载工作副本；原始上传目录不能直接作为容器内源文件路径。
- Windows 没有可用 Docker 引擎时，应在服务器执行沙箱验证并如实说明本机跳过情况。
- 初次真实基线曾因智能体 420 秒超时失败。#13 已部署源码限读与 600 秒预算，后续 12 个任务均成功，不应继续使用失败任务作为统计依据。
- 若报告计入了附近原有问题，核查基线过滤和候选标题，不能只看表格是否达到 6 项。
