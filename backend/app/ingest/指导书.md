# 工程处理与参考代码差异分析

## 1. 模块职责与处理流程

工程处理模块把上传文件整理为可供后续评测使用的工程目录，并提供文件清单、带行号的源码片段和参考代码差异。模块位于 `backend/app/ingest/`，只使用 Python 标准库完成文件处理，不承担编译、运行、静态分析或评分。

处理顺序为：保存上传文件 → 安全检查与过滤 → 识别工程 → 复制工程原件 → 列出或读取源码 → 匹配参考实验 → 生成差异证据。后续模块通过项目编号选择工程，读取整理后的原件；编译和扫描需要修改代码时，使用各自的工作副本。

| 文件 | 主要内容 |
|---|---|
| `__init__.py` | 导出约定的五个函数和 `PathInvalidError` |
| `upload.py` | 上传展开、过滤、工程识别和元信息统计 |
| `source.py` | 相对路径校验、文件清单和源码读取 |
| `reference.py` | 参考实验匹配、差异范围和改动标记 |
| `NOTES.md` | 实现问题、验证命令和验收记录 |

输入文件位于 `tasks/{task_id}/upload/`。整理后保留两层目录：`unpacked/` 保存过滤后的展开结果；`projects/p1/`、`projects/p2/` 等保存各工程原件。结果中的文件路径均相对工程根目录，使用 `/` 分隔，行号从 1 开始。

## 2. 安全展开与工程识别

### 2.1 上传检查

输入可以是一个 zip，或一组 `.c`、`.h` 文件。块 1 检查上传扩展名、文件数量和上传体积，块 2 继续检查展开内容。

| 检查内容 | 处理结果 |
|---|---|
| 损坏、加密或不支持的压缩包 | `UPLOAD_BAD_ZIP` |
| 绝对路径、上级目录、符号链接和不安全文件名 | `UPLOAD_UNSAFE_PATH` |
| 展开总量超过 100MB，或文件数超过 5000 | `UPLOAD_TOO_LARGE` |
| 过滤后没有 `.c` 文件 | `NO_SOURCE_FOUND` |

路径校验同时考虑 Windows 和 Linux。除了 `../` 和绝对路径，还拒绝盘符、反斜杠、Windows 设备名、备用数据流以及重复路径。文件与目录的名称冲突也不能静默覆盖。阶段 3 的修补进一步检查各级父目录大小写，例如 `Demo/a.c` 与 `demo/b.h` 在 Windows 上可能被合并，而在 Linux 上是不同目录，因此统一拒绝此类输入。

压缩包按 64KB 块读取，读取过程中累计字节数，超过上限立即停止。被过滤文件仍接受路径检查并计入总量，不能把文件放入 `build/` 等目录来绕过限制。每个可保留文件最多暂存 1MB，超过该值就过滤。

整理过程先写入任务内的临时目录，成功后再发布 `unpacked/` 和 `projects/`。无效上传不会形成可供后续评测使用的完整工程；已有处理结果拒绝覆盖。

### 2.2 中文名称与无关文件过滤

部分 Windows 压缩包使用 GBK 保存中文名称，但没有设置 UTF-8 标志。此时把 zipfile 解码后的名称重新编码成 cp437 字节，先尝试 UTF-8，失败后尝试 GBK。测试直接构造未设置标志的两种编码，确认 `创新功能实现.md` 能正确恢复。

过滤目录包括 `.git`、`__MACOSX`、编辑器配置、`build`、`cmake-build-*` 和 `node_modules`；过滤文件包括操作系统缓存、编译产物、嵌套压缩包以及超过 1MB 的文件。过滤数量写入 `ignored_count`。

### 2.3 工程根与属性

目录满足以下任一条件时作为完整工程根：存在 `src/CMakeLists.txt`；或根目录的 `CMakeLists.txt` 含 `project(`。先检查父目录，选中工程根后不再把它的子目录重复识别为工程。

没有完整工程时生成一个片段工程，根目录取所有 `.c` 文件的公共父目录。工程编号按根路径字典序分配为 p1、p2 等。完整工程以外的文件不进入任何工程，其数量计入忽略数。

架构从 CMakeLists、汇编、链接脚本和 C 文件中的标识判断：出现 aarch64、armv8 或 cortex-a 时为 aarch64，出现 riscv 时为 riscv64，否则为 unknown。只有完整 aarch64 工程的 `buildable` 为 true；片段工程可以继续读取和分析源码，但不能据此声明可编译。

## 3. 文件清单与源码证据

`list_files` 按相对路径排序，返回文件大小、行数和语言。行数只按 LF 计算，CRLF 视为一次换行；文件末尾没有换行也计一行，空文件为 0 行。未使用 `splitlines()`，避免把垂直制表符等字符额外算作换行。

`read_source` 先检查相对路径，再对目标执行 `resolve()`，确认解析后的文件仍在工程目录内。目录、不存在的文件、含 NUL 的二进制文件以及无效行范围均抛出 `PathInvalidError`。阶段 3 修补还将路径解析时的权限错误和链接循环转换为该异常，便于块 1 返回统一错误响应。

读取文本采用 UTF-8，并替换无法解码的字节。起始行小于 1 时取 1，结束行超过末尾时截断，每次最多 200 行。输出格式示例如下，内容为合成示例：

```text
    1 | int main(void) {
    2 |     return 0;
    3 | }
```

模块返回的 `evidence_id` 为空，由块 1 的工具层分配 S1、S2 等编号。这使文件读取与一次具体工具调用的证据编号分开管理。

## 4. 创新点 C：参考代码差异分析

### 4.1 选择参考实验

参考代码固定为仓库 `os2024_exp_redo_kp` 的提交 `0bd1ef59f32867842f0c3047a58d62bced82d54b`。参考根目录包含 lab1、lab2、lab4 等实验目录，每个实验目录的内部结构与学生工程根一致。

对每个 lab，把学生文件的相对路径集合与参考文件的相对路径集合求交，交集大小作为候选得分。选择同路径文件最多的实验；数量相同时按实验编号的数值取较大的一个，避免字符串比较把 lab8 排在 lab10 之后。参考目录缺失、没有实验目录或所有候选得分均为 0 时返回 `unsupported`，说明无法建立有效基线。

此方法判断的是文件结构与哪一份参考实验最接近，不依据文件名中的个人信息，也不把基线匹配解释为代码来源鉴定。

### 4.2 文本归一化

比较前对每行移除 CR 和行尾空白，再移除文件末尾的空行。行首缩进、中间空行和其他内容仍参与比较，避免把真实修改抹掉。

学生侧或参考侧含 NUL 的文件不进行文本比较，跳过数量写入 `note`。这些文件仍参与路径匹配，但不进入差异文件列表，后续改动标记返回未知；不能把未比较的文件当成“基线未变”。

### 4.3 文件状态与改动范围

| 情况 | 状态和统计 |
|---|---|
| 基线不存在该相对路径 | `added`；新增行数为归一化后的行数 |
| 两侧归一化内容相同 | `same`；新增、删除行数为 0 |
| 路径相同但内容不同 | `modified`；计算增删改范围 |

内容不同时调用 `difflib.SequenceMatcher(None, ref, stu, autojunk=False)`。关闭自动忽略高频元素的策略，使重复较多的源码行也参与匹配。

对操作码 `(tag, i1, i2, j1, j2)`，参考侧区间是 `[i1, i2)`，学生侧区间是 `[j1, j2)`：

- `insert` 或 `replace`：学生侧闭区间为 `[j1 + 1, j2]`，加入 hunks，新增行数累加 `j2 - j1`。
- `delete` 或 `replace`：删除行数累加 `i2 - i1`。
- `equal`：不生成改动区间。

仅删除内容时，学生侧没有新增行，因此 hunks 为空。新增空文件仍标为 added，但行数为 0、hunks 为空，不能构造无效的 1 到 0 行范围。结果只列学生当前存在的文件，不额外列出仅参考侧存在的文件。

### 4.4 证据编号与缺陷标记

文件按路径排序，只给 modified 和 added 文件依次分配 D1、D2 等证据编号；same 文件的编号为空。编号、行范围与统计共同构成 `DiffResult`，由块 1 保存并提供给差异工具接口。

`change_flags` 返回两个标记：学生改动行、基线未变文件。

| 输入情况 | 返回值 |
|---|---|
| 无对比结果、状态不是 passed、文件不在结果中 | `(None, False)` |
| 文件为 same | `(False, True)` |
| modified/added 且行号位于任一闭区间内 | `(True, False)` |
| modified/added 但行号不在改动区间内 | `(False, False)` |

修改文件中的未修改行不等于“整个文件与基线相同”。评分是否扣分由其他模块决定，块 2 只提供这两个事实标记。

### 5.3 测试证据与范围

阶段 1、2 在 Windows 和 Linux 上均完成 140 项测试。阶段 3 增加 4 个回归用例，Windows 块 2 专项结果为 98 passed，Linux 全部非 Docker 测试为 182 passed、24 deselected。24 个未运行项为块 3 的 Docker 测试，不属于本轮路径修补验证。

合入块 3 后，Windows 全量测试有 8 项平台相关失败，涉及符号链接权限、os.getuid 和默认 GBK 解码；相同非 Docker 测试在 Linux 通过。这些测试未被删除或弱化。完整记录见阶段 3 PR 和 NOTES。

截至本次验证，生产服务的 ingest、diff、buildrun 为真实模块，analyze、scoring 为 mock。本地和服务器 TestClient 流水线测试中，编译、扫描、智能体、评分仍使用 mock；这些测试证明块 2 与公共流水线的数据连接正常，不代表整个评测系统最终验收。

## 6. 复现与交接

在仓库根目录的 PowerShell 中运行块 2 测试：

```powershell
$env:KE_REF_ROOT = (Resolve-Path backend/data/ref/os2024_exp_redo_kp).Path
backend/.venv/Scripts/python -m pytest -q backend/tests/ingest
```

必须显式设置参考目录，因为公共测试配置会把 DATA_ROOT 指向临时目录，从而改变默认 REF_ROOT。样例从 `config.SAMPLES_ROOT` 读取；CI 没有样例或参考数据时按规范跳过相应本地验收测试，不能把这种跳过报告成真实样例验证通过。

服务器开发只使用个人目录 `~/dev/Liu/`，从 `/data/kernel-eval/samples` 和 `/data/kernel-eval/ref/os2024_exp_redo_kp` 只读获取已有数据。临时文件和测试运行数据放在个人目录内。生产代码、配置和服务由块 1 管理，块 2 不直接修改。

阶段 3 的父目录大小写与路径解析修补位于独立 PR #6，需审核合并后部署；本指导书作为阶段 4 的独立文档交付。样例源码、个人信息、密钥和运行数据均不进入提交。
