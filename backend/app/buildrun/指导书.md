# 编译与运行模块搭建与验证

本章说明如何搭建 MiniEuler 的交叉编译和 QEMU 运行环境，独立验证块三，并把结果交给公共流水线。学生工程先复制到工作目录，再在一次性 Docker 容器中编译和运行；原始工程保持不变。模块只提供编译和运行证据，最终评分由评分模块完成。

## 环境要求

推荐使用 Ubuntu 24.04 的 x86_64 服务器，四核、8GB 内存和约 80GB 磁盘即可串行执行本块测试。交叉工具链的宿主架构是 x86_64，目标架构是 AArch64；不要把工具链的目标架构与云服务器的 CPU 架构混淆。

环境包含 Python 3.12、Docker、CMake、QEMU 和 Arm GNU Toolchain 13.3.Rel1。CMake、QEMU、clang 和工具链安装在沙箱镜像中，宿主只需要 Docker 和后端 Python 依赖。现有镜像可用时直接复用，不必重建。

首次配置独立测试机时，由管理员安装 Docker、Python 虚拟环境工具和 rsync。不要在组里的共享服务器重复安装或升级这些软件。

```bash
sudo apt-get update
sudo apt-get install -y docker.io python3-venv rsync
sudo useradd --create-home --shell /bin/bash kernel-eval-dev
sudo usermod -aG docker kernel-eval-dev
```

后续测试使用普通用户执行，账号需要能够调用 Docker。公共执行器会拒绝以宿主 root 身份运行学生工程。在管理员会话中可用 `sudo -iu kernel-eval-dev` 切换用户；新加入 docker 组后重新登录，确保组权限生效。为测试账号准备可写的代码、样例和临时工作目录。

## 构建沙箱镜像

从 Arm 官方站点下载 `arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-elf.tar.xz`，放到仓库 `sandbox/` 下并命名为 `aarch64-none-elf.tar.xz`。文件不进入 Git。

```bash
cd sandbox
curl -fL -o aarch64-none-elf.tar.xz \
  https://developer.arm.com/-/media/Files/downloads/gnu/13.3.rel1/binrel/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-elf.tar.xz
docker build -t kernel-eval-sandbox:0.1 .
```

仓库 Dockerfile 默认配置了腾讯云 Ubuntu 软件源。在其他云上需要使用可访问的软件源时，通过构建参数覆盖即可：

```bash
docker build --build-arg APT_MIRROR=http://repo.huaweicloud.com/ubuntu \
  -t kernel-eval-sandbox:0.1 .
```

镜像中 `/opt/toolchain` 指向统一的交叉工具链目录，构建工作副本里的工具链路径会改写到这里。镜像标签应与 `KE_SANDBOX_IMAGE` 一致，默认是 `kernel-eval-sandbox:0.1`。修改共享镜像时，必须同时验证编译运行和静态分析使用方；本次交付没有修改 Dockerfile。

## 无法访问 Docker Hub 时的本机中转

可以在能访问外网的开发机上取得 Canonical 官方 Ubuntu 24.04 amd64 容器根文件系统，核对官方 SHA256 清单，再传到测试机导入。无需公开仓库、开放代理端口或上传登录凭据。

在开发机的临时目录执行：

```bash
curl -fL -o ubuntu-noble-oci-amd64-root.tar.gz \
  https://partner-images.canonical.com/oci/noble/current/ubuntu-noble-oci-amd64-root.tar.gz
curl -fL -o SHA256SUMS \
  https://partner-images.canonical.com/oci/noble/current/SHA256SUMS
python3 - <<'PY'
import hashlib
from pathlib import Path
name = "ubuntu-noble-oci-amd64-root.tar.gz"
expected = next(line.split()[0] for line in Path("SHA256SUMS").read_text().splitlines()
                if line.split()[-1].lstrip("*") == name)
assert hashlib.sha256(Path(name).read_bytes()).hexdigest() == expected
print("SHA256 校验通过")
PY
```

校验通过后通过 scp 或 rsync 传到测试服务器的专用工作目录，在服务器执行：

```bash
docker import --platform linux/amd64 --change 'CMD ["/bin/bash"]' \
  ubuntu-noble-oci-amd64-root.tar.gz ubuntu:24.04
```

再把工具链压缩包传入 `sandbox/`，按上一节构建。这样基础镜像不再需要从 Docker Hub 拉取，安装软件仍通过国内 Ubuntu 镜像源完成。开发机下载后的文件也应核对传输前后摘要。

## 编译与运行流程

块二传入 `Project` 和只读工程目录。`build()` 对 `buildable=false` 返回 `unsupported`，其余工程通过 `prepare_workspace()` 复制到工作目录，改写工具链路径并清除复制来的旧 `build/` 产物。工作目录不能与原始工程重叠，工程中不能存在符号链接。

如果存在 `src/CMakeLists.txt`，CMake 源目录选 `src`，否则选工程根。配置启用 `CMAKE_EXPORT_COMPILE_COMMANDS=ON`，编译使用两个并行任务。产物按 `build/miniEuler`、`build/miniEuler.elf`、其他 ELF 的顺序查找。只有退出码为零且找到工作目录内的有效产物才算编译成功。

构建诊断按出现顺序编号为 B1、B2 等，最多保存一百条。工程内警告计入 `warnings`，链接器等工程外警告不计入这个值。所有识别到的错误计入 `errors`，包括规范化后的 fatal error。证据列表的数量上限不会截断统计总数。

编译默认限时 180 秒。超时返回 `failed`，并附加“编译超时”错误。原始构建输出上限为 256KB，被截断时日志末尾注明原始字节数；`log_tail` 保存最后三千个字符。

`run()` 只处理编译通过的工程，否则返回 `skipped`。它读取启动脚本中的最后一个 GIC 参数；缺失时查找源码中的参数或 `GIC_VERSION`，最后默认使用 GIC 2。只读取脚本内容，不执行学生启动脚本。QEMU 参数固定包含 `-nic none`，避免缺少网络 ROM 影响内核启动。

每次运行默认二十秒，启动五秒后发送 `top`，再每隔两秒发送一条命令。命令以回车结尾；除 `top`、`tick` 外，从 shell 源码中的字符串比较、命令表和连续字符比较提取自定义命令，去重后合计最多六条。样例一的结果为 `top`、`tick`、`mem`。

没有内核串口输出时，切换 GIC 2 和 GIC 3 重试一次。QEMU 自己的提示不算内核启动输出；退出码 124 表示运行窗口结束，不直接算失败。整个运行调用在默认一分钟预算内结束。

串口结果会统一换行、移除空字符并合并空行。只有提示符后紧跟已发送命令的回显，才确认它是 shell 提示符。启动输出编号为 R1，命令输出从 R2 开始，每段最多四千个字符。

异常规则是：非空行重复至少五十次记 `EXC_STORM`，输出超限记 `OUTPUT_TRUNCATED`，没有内核输出记 `NO_OUTPUT`。有内核输出且没有刷屏时，运行状态为 `passed`；这只表示本次启动和刷屏检查通过，其他功能的完整性仍由后续评审判断。功能提示 `F_UART`、`F_TIMER`、`F_TASK`、`F_SHELL` 也只是供智能体参考的证据。

## 沙箱资源与清理

每次调用使用独立、随机命名的一次性容器，禁用网络，以普通用户 UID 运行，移除 capabilities 并禁止新增权限，限制两个 CPU、1GB 内存和 256 个进程。容器只挂载本任务的工作副本。

执行器在输出超过上限后仍持续读取管道，只丢弃超出的缓冲内容，避免学生刷屏造成内存持续增长或管道堵塞。输入线程支持取消，内核或命令提前退出时不会遗留等待输入的线程。结束后清理本次容器，超时返回 `timed_out=true` 和空退出码；清理本身失败则抛出工具错误。

容器带有 `kernel-eval=1` 和用户归属标签。`cleanup_stale()` 仅清理当前用户创建、带项目标签且运行超过十分钟的容器，不自动清理其他服务的资源。它可由运维流程主动调用，本模块不会自动安排定时任务。

## 测试与复现

不需要 Docker 的测试可在本地和 CI 运行：

```bash
cd backend
.venv/bin/python -m pytest -q
```

真实验收必须在有镜像的 Linux 服务器上，以普通用户执行：

```bash
cd backend
KE_REQUIRE_SANDBOX=1 KE_SAMPLES_ROOT=/你的样例绝对路径 \
  .venv/bin/python -m pytest -q tests/buildrun
```

再运行全量后端测试，确认没有影响其他模块：

```bash
KE_REQUIRE_SANDBOX=1 KE_SAMPLES_ROOT=/你的样例绝对路径 \
  .venv/bin/python -m pytest -q
```

缺少 Docker、守护进程或镜像时，本地和 CI 会跳过真实沙箱测试；设置 `KE_REQUIRE_SANDBOX=1` 后会直接报错，不能把跳过当成验收通过。样例目录也必须齐全，检查最终输出中是否有 skipped。

测试覆盖两份完整样例、全部十一个 lab、源码损坏、命令交互、GIC 识别与重试、独立死循环内核、独立刷屏内核、CMake 配置卡死、输出字节统计、非 root 身份和超时容器清理。

## 当前样例与说明的差异

当前分发的 lab6_pro 在独立测试机上的表现不稳定：前两次运行二十秒，两个任务均打印完成信息，总输出约 4KB；后续运行触发任务说明中的 `Catch a exception.` 刷屏，日志达到 256KB 保留上限，模块正确标记异常。因此该原样例测试按实际串口证据严格校验正常和异常两种结果，不把某一次输出当作固定预期。

异常刷屏能力由本块自写的最小故障内核另行验证，要求返回 `failed`、同时包含 `EXC_STORM` 和 `OUTPUT_TRUNCATED`、保留日志不超过 256KB，并在三十秒内结束。这份故障内核不包含往届学生源码。

若后续更换为其他样例版本，需要先核对实际源文件和运行日志。异常触发条件尚未定位，不能按目录名称强制判定运行失败。当前样例标识和两种输出的复现记录见同目录 `NOTES.md`。

## 交接

模块签名、结果模型和公共沙箱函数签名均保持不变。日志路径在模块中指向传入日志目录里的实际文件，由公共流水线转换为任务相对路径。编译后的 `compile_commands.json` 和内核产物保留在工作目录，供后续步骤使用。
